# 心理健康对话评估智能体总体设计方案

版本：V1.0（研究与原型设计稿）  
日期：2026-07-21  
适用场景：高校心理健康初筛、信息采集、风险提示、后台静默报告与飞书自动上传  
设计依据：P1-P6、S1-S5 共 11 份访谈，183 条开放编码，Miro RQ1/RQ2 整理结果，20 项智能体设计需求  
文档状态：供组内评审与原型实现使用，不作为临床规范或正式诊疗方案

## 1. 方案摘要

本项目拟建设一个面向高校学生的“心理健康对话评估助手”。系统通过自然语言对话了解学生当前困扰，在尽量减少问卷感的前提下，逐步采集主诉、情绪、睡眠饮食、学习与人际功能、既往求助经历、支持系统及危机风险等信息，形成结构化的初步评估报告，并在对话结束后由系统后台静默上传至飞书多维表格。

系统的核心价值不是替代心理咨询师或精神科医生，而是完成四项辅助工作：

1. 以主诉驱动的方式收集评估所需信息。
2. 对自伤、自杀、伤人及疑似严重精神症状进行优先识别和安全分流。
3. 将自然语言回答整理成可解释、可追溯的结构化记录。
4. 形成统一格式的后台报告记录，便于后续统计、原型调试、汇报展示和系统迭代。

本方案将 RQ1 转化为“系统需要评估什么”，将 RQ2 转化为“系统如何安全、可控地完成评估”。

## 2. 研究依据与设计边界

### 2.1 研究依据

当前设计依据包括：

- 6 份心理咨询师/高校心理工作者访谈与 5 份精神科相关访谈。
- 183 条开放编码及全量主题总结。
- Miro 中关于评估信息要素、判断逻辑、处置决策、边界命名、误导风险、危机闭环和人机协作的整理。
- 20 项需求清单，其中 P0 聚焦系统边界、主诉采集、危机响应、资源白名单和非诊断性报告。

证据链为：

```text
访谈原文 -> 开放编码 -> 主题归纳 -> 需求条目 -> 功能模块 -> 对话与安全规则 -> 报告字段
```

### 2.2 明确边界

系统可以：

- 倾听并梳理用户当前困扰。
- 采集初步心理评估信息。
- 使用经过批准的短量表辅助筛查。
- 标记风险线索、信息缺口和建议分流方向。
- 生成用于后台记录和后续汇总的结构化报告。
- 在风险场景下提示联系现实支持与经审核的专业资源。

系统不可以：

- 宣称自己是心理咨询师、精神科医生或紧急救援人员。
- 输出确定性疾病诊断或排除诊断。
- 开具、调整或停止药物。
- 提供替代正式心理咨询或精神科诊疗的承诺。
- 仅凭关键词、单次量表分数或单段文本断定严重程度。
- 在危机场景下继续普通测评、放松训练或泛化安慰。
- 使用未经审核的热线、医院、链接或其他危机资源。

### 2.3 当前待确认项

以下内容尚未由项目组正式确认，应作为配置项管理：

1. 产品最终名称及对外表述。
2. 学生端反馈和后台上传报告分别包含哪些内容。
3. 校内心理中心、辅导员、校医院、属地医院、热线和紧急服务白名单。
4. 学生端展示哪些校内心理资源、服务时间和提示文案。
5. 知情同意文本、隐私政策、数据保存期限和伦理审查要求。
6. 可使用的量表、授权条件、计分方式与结果展示范围。
7. Coze 工作流可用能力、数据库和飞书多维表格的字段及权限。

在上述事项确认前，原型只能使用占位配置，不得模拟真实危机联动已经建立。

## 3. 目标、非目标与成功标准

### 3.1 产品目标

| 编号 | 目标 | 可验证结果 |
| --- | --- | --- |
| G1 | 自然收集关键信息 | 用户无需连续填写长问卷，系统仍能形成结构化字段 |
| G2 | 风险优先 | 任意阶段出现风险线索，都能中断普通流程并进入安全评估 |
| G3 | 降低误导 | 不输出诊断、不做治疗承诺，问题保持中性且允许跳过 |
| G4 | 支持后台自动上传 | 报告保留原始依据、信息缺口、风险规则、资源提示和上传状态 |
| G5 | 可实施与可测试 | 功能可映射到 Coze 节点、规则库、知识库和输出字段 |

### 3.2 非目标

- 不以聊天时长或情绪黏性为目标。
- 不追求单轮完成全部心理评估。
- 不在当前阶段建立医学诊断模型。
- 不把“低风险”解释为“没有风险”。
- 不在缺少伦理、权限和响应团队的情况下自动通知第三方。
- 不在首版实现语音、视频、表情或其他多模态判断。

### 3.3 成功标准

首版原型应达到以下最低标准：

1. 边界声明、知情说明、开放式主诉、基础评估、固定安全筛查、总结确认和报告生成链路可运行。
2. 用户在任意节点表达明确危机线索时，普通流程被暂停。
3. 报告不出现确定性诊断、臆测性病因或未在对话中出现的事实。
4. 每个风险提示可追溯至用户表达、追问结果或经批准的量表结果。
5. 信息不足时输出“待确认”，不使用模型猜测补全。
6. 系统能够自动生成后台报告、完成基础校验并上传飞书留档。

## 4. 用户、角色与使用场景

### 4.1 角色

| 角色 | 主要任务 | 权限边界 |
| --- | --- | --- |
| 学生用户 | 自主表达、接受初步筛查、查看适合本人阅读的反馈 | 可跳过、暂停、更正；不直接查看专业端内部风险推理 |
| 学校心理健康中心资源 | 为学生端提供可联系的校内心理支持渠道 | 系统只展示已确认联系方式，不承诺主动联系或处置 |
| 项目管理员 | 配置资源、量表、权限、版本和上传字段 | 不默认拥有查看全部对话正文的权限 |
| 系统维护人员 | 维护平台、日志和可用性 | 原则上仅接触去标识化技术日志 |
| 智能体 | 采集、整理、提示风险、生成草稿 | 无诊断权、无强制处置权、不得越权通知 |

### 4.2 核心场景

1. 学生主动发起一次心理状态梳理。
2. 学生围绕学业、关系、家庭、睡眠、就业等具体困扰进行对话。
3. 系统根据主诉调用经批准的短量表或结构化问题。
4. 系统生成学生端温和反馈和后台结构化报告。
5. 系统调用工作流，将后台报告自动上传至飞书多维表格。
6. 对话中出现危机线索，系统立即转入安全确认与资源引导。

## 5. 设计原则

### 5.1 主诉驱动，字段补全

先让用户说明“最近最困扰的事情”，系统沿用户叙述展开，再补充持续时间、频率、强度、功能影响和安全状况。不能把字段表直接变成机械问卷。

### 5.2 风险监测全程在线

危机识别不是单独放在对话末尾的一道题，而是覆盖每轮输入的独立安全通道。只要出现明确或含蓄风险线索，就暂停普通流程并进入危机状态机。

### 5.3 有限共情，不假装治疗关系

回应应承认用户正在承受的困难，随后澄清事实或确认安全。避免“我完全理解你”“我会一直陪着你”“你一定会好起来”等无法兑现的表达。

### 5.4 证据与结论分离

报告分别记录“用户说了什么”“系统如何结构化”“系统提示什么风险”“哪些信息仍缺失”。风险提示不得伪装为事实或诊断。

### 5.5 最小必要采集

只收集与评估、分流和安全有关的信息；敏感字段必须说明用途。对用户跳过的信息记录“未提供”，不得反复逼问。

### 5.6 后台静默报告与资源提示

本项目最终方案不设置人工复核闭环。AI 负责完成对话初筛、结构化整理和后台报告生成；对话结束后，报告自动上传至飞书多维表格。对潜在安全问题，学生端只提供学校心理健康中心老师联系电话等资源信息，不承诺自动告警、主动联系或第三方处置。

## 6. 总体架构

```text
学生端对话界面
      |
      v
会话编排与状态管理 ---- 知情同意/暂停/退出
      |
      +---- 全程安全监测 ---- 危机状态机 ---- 白名单资源/校内联系方式提示
      |
      +---- 主诉理解 ---- 动态追问 ---- 字段完整性检查
      |
      +---- 量表路由 ---- 授权量表知识库 ---- 计分与解释
      |
      v
结构化个案记录 ---- 报告生成 ---- 飞书自动上传 ---- 留档/统计
      |
      v
权限、审计、版本与质量监测
```

架构采用“生成模型负责语言表达，确定性规则负责安全门控和关键计算”的原则。危机触发、量表计分、资源选择、权限和报告必填校验不得只依赖大模型自由生成。

## 8. 核心信息模型

每个字段必须同时记录“值、来源、状态和时间”，以区分用户原话、系统归纳和后台记录。

| 信息域 | 关键字段 | 状态要求 |
| --- | --- | --- |
| 会话信息 | 会话编号、时间、渠道、版本、知情状态 | 必填 |
| 基础画像 | 年级、学习/工作状态、居住状态 | 可选或按需采集 |
| 主诉 | 当前困扰、求助目标、优先议题 | 必填 |
| 时间维度 | 起始时间、持续时长、频率、近期变化 | 主诉相关时必填 |
| 情绪与认知 | 情绪类型、强度、担忧、消极想法、注意力 | 按主诉采集 |
| 行为与身体 | 活动、回避、睡眠、食欲、躯体不适 | 按主诉采集 |
| 功能影响 | 学习、工作、人际、生活自理 | 至少确认主要功能域 |
| 校园情境 | 学业、宿舍、关系、家庭、升学就业 | 按相关性采集 |
| 既往与支持 | 既往咨询/就医/用药、可信任的人、当前支持 | 风险或转介判断时重要 |
| 安全风险 | 想法、计划、工具、时间、行为、既往史、独处、保护因素 | 触发后按危机规则采集 |
| 量表 | 名称、版本、授权状态、回答、分数、时间 | 使用时必填 |
| 报告与上传 | 摘要、依据、缺口、资源提示、上传状态 | 必填 |

字段状态统一使用：`已确认`、`用户不确定`、`用户拒答`、`未询问`、`信息冲突`、`不适用`。禁止把空值自动解释为否定答案。

## 9. 核心决策逻辑

### 9.1 信息采集逻辑

```text
用户自由表达
-> 识别当前主诉和已有字段
-> 检查即时风险
-> 选择一个最相关的信息缺口
-> 进行一次中性追问
-> 更新结构化记录
-> 判断继续追问、量表辅助、总结或安全分流
```

每轮最多聚焦一个主要问题；只有在确认选项有助于降低用户负担时才提供少量选项。

### 9.2 风险分流逻辑

系统内部可使用以下工作流标签，但必须明确它们不是临床风险诊断：

- `R0 未见明确即时风险`：当前材料未发现明确即时风险，仍保留不确定性。
- `R1 需要关注`：存在消极想法、明显功能下降或其他风险因素，学生端应提示可联系学校心理健康中心。
- `R2 高度关注`：存在较强风险意念、方法可及、既往行为、严重精神症状或安全环境不足，应立即提示联系现实支持、校内心理资源或紧急服务。
- `R3 紧急`：行为正在发生、计划近期实施、已经受伤/服药或无法保证当前安全，应直接引导联系当地紧急服务和现场可信任人员。
- `RX 信息不足`：关键问题未回答、表达矛盾或系统无法可靠判断，按保守原则记录为安全状态未完成确认。

标签仅用于决定下一步工作流，不对用户直接显示代码。

### 9.3 量表路由逻辑

1. 量表必须来自经项目组批准且具备合法使用条件的清单。
2. 先完成主诉理解和基本安全检查，再决定是否使用。
3. 使用前说明目的、预计耗时、结果用途和可拒绝性。
4. 抑郁、焦虑、睡眠等议题分别路由到对应短量表；不默认完整投放 SCL-90。
5. 计分由确定性程序完成，不由大模型心算。
6. 量表结果只作为辅助证据，不能覆盖用户原始叙述或系统边界。
7. 涉及自伤条目的阳性回答立即进入危机流程，不能等量表结束。

## 10. 自动报告与上传流转

### 10.1 报告状态

```text
会话结束 -> 字段冻结 -> 自动校验 -> 飞书上传中 -> 上传成功/上传失败 -> 留档或重试
```

### 10.2 必须记录的安全关注状态

- `R0`：当前对话未披露明确即时风险。
- `R1/R2/R3`：存在不同程度需关注安全线索，学生端应提供学校心理健康中心联系方式等资源。
- `RX`：安全状态未完成确认，不能写成否认风险。
- 上传失败：记录错误信息并允许重试，不在学生端暴露技术细节。

### 10.3 自动上传要求

1. 报告只写本次对话中明确提供或经用户确认的信息。
2. 每个关键字段保留来源、状态和时间。
3. 报告必须经过诊断性措辞、虚构内容和资源字段校验。
4. 飞书记录必须包含上传时间、报告版本和安全关注状态。
5. 学生端不展示完整报告、内部风险标签和飞书记录。

## 11. 知识库与资源配置

知识库至少拆分为四类，避免不同风险等级混用：

| 库 | 内容 | 调用限制 |
| --- | --- | --- |
| KB-A 边界与服务说明 | 产品用途、隐私、知情同意、常见问题 | 可直接面向用户 |
| KB-B 评估与量表 | 批准量表、题目、计分、解释、版本和授权 | 仅由量表路由模块调用 |
| KB-C 心理教育 | 睡眠、压力、情绪调节、求助准备等审核内容 | 低风险且与主诉匹配时调用 |
| KB-D 危机资源白名单 | 校内联系人、热线、医院、紧急服务、服务时间 | 仅危机模块调用，需定期复核 |

每条资源需记录地区、服务对象、服务时间、联系方式、审核人、审核日期、失效日期和替代资源。资源过期或地区不匹配时不得推送。

## 12. 隐私、伦理与安全要求

1. 在开始前提供清晰的知情说明，并记录同意状态和版本。
2. 明确用户可以跳过、暂停、退出和更正。
3. 只采集完成评估和安全分流所需的最少信息。
4. 身份信息与对话内容尽量分离保存，以随机会话编号关联。
5. 权限采用最小授权原则，区分查看、上传、导出和配置权限。
6. 对话正文、报告、飞书上传和导出操作均需记录审计日志。
7. 日报、演示和研究材料默认使用去标识化内容，不粘贴可识别个人信息。
8. 数据保存期限到期后按项目制度删除或匿名化。
9. 在正式试用前完成伦理、法律、学校管理和专业安全评审。
10. 不使用学生真实危机案例进行公开演示。

## 13. Coze 原型落地映射

| 设计对象 | Coze/低代码实现建议 | 备注 |
| --- | --- | --- |
| 系统边界 | 系统提示词固定区 | 不允许被用户指令覆盖 |
| 对话状态 | 会话变量或工作流数据对象 | 保存字段状态和当前阶段 |
| 风险监测 | 每轮输入前置分类节点 + 规则节点 | 高风险优先级高于普通生成 |
| 动态追问 | 字段缺口选择节点 + 语言生成节点 | 生成模型只负责自然表达 |
| 量表 | 独立工作流/插件 | 题目、计分和阈值版本化 |
| 危机资源 | 独立白名单知识库 | 禁止通用联网检索替代 |
| 报告 | 结构化 JSON 输出 + 模板渲染 | 先校验后生成可读文本 |
| 自动报告上传 | 飞书多维表格或后续后台 | 高风险信息需严格控权 |
| 审计 | 会话日志、规则命中、版本号 | 便于复现和纠错 |

当前原型不应把“模型直接生成一段报告”视为完整实现。最低可控链路应为：结构化字段提取、规则校验、报告模板渲染、飞书自动上传。

## 14. 测试与评价方案

### 14.1 安全测试

- 明确自杀计划、含蓄死亡表达、既往自伤、正在服药过量、伤人意图。
- 幻听、妄想、明显躁狂/轻躁线索。
- 否定、双重否定、引用他人话语、玩笑和反事实表达。
- 用户拒绝回答、突然退出、重复改变答案。
- 危机资源过期、地区不匹配、联系方式缺失或飞书上传失败。

安全测试重点关注漏报。任何漏报均视为 P0 缺陷。

### 14.2 对话质量测试

- 是否先开放表达，再结构化追问。
- 是否重复询问已确认内容。
- 是否使用暗示性、评判性或诊断性语言。
- 是否一次提出过多问题。
- 是否能识别“还行”“不太想活”“有点撑不住”等模糊表达并澄清。
- 是否允许跳过、暂停和更正。

### 14.3 报告质量测试

- 字段完整率与信息缺口标记准确率。
- 原始表达与结构化摘要的一致性。
- 风险提示的证据可追溯率。
- 不当诊断表述出现率。
- 飞书上传成功率、字段完整率和报告生成耗时。
- 学生版是否避免暴露内部推理和不必要敏感信息。

### 14.4 建议验收阈值

正式阈值应由项目组结合学校心理健康资源和数据制度共同确定。原型阶段建议至少做到：

1. 预设高风险测试样例全部触发危机分支。
2. 报告关键事实与测试脚本一致，不允许虚构字段。
3. 所有风险标签均能回溯至至少一条明确依据或“信息不足”说明。
4. 所有危机资源均来自有效白名单。
5. 所有报告均带系统边界、安全关注状态和飞书上传状态。

## 15. 分阶段实施计划

### 阶段 A：可评审设计稿

- 完成总体方案、状态流程、系统提示词、危机规则和报告模板。
- 由项目组和相关专业老师审核边界、问题措辞、量表与风险分流。
- 由项目负责人确认报告字段、资源白名单和飞书上传边界。

### 阶段 B：最小可用原型

- 在 Coze 实现开场、主诉、动态追问、安全筛查、总结和结构化输出。
- 接入一项或两项获准的短量表作为验证，不追求量表覆盖面。
- 使用模拟案例测试，不接触真实高风险用户。

### 阶段 C：封闭测试

- 使用专家编写的标准化测试脚本进行安全和对话评测。
- 使用标准化模拟案例记录误报、漏报和不当话术。
- 修正规则、提示词和报告模板，并冻结版本。

### 阶段 D：受控试用

- 仅在伦理、隐私、资源和数据权限条件满足后开展。
- 明确试用范围、退出机制、资源提示边界和事件复盘流程。

## 17. 评审结论与下一步决策

该方案已经将访谈发现转为可实施的模块、状态、数据和安全约束，但仍属于研究原型设计。进入真实用户测试前，项目组至少需要完成以下决策：

1. 由学校心理健康中心老师确认风险分层、危机追问和量表策略。
2. 确认危机资源白名单和学生端展示方式。
3. 确认学生端反馈和后台上传报告的内容差异。
4. 确认隐私、伦理、数据权限和保存制度。
5. 确认 Coze 原型与飞书/自研平台之间的数据边界。

只有完成上述确认后，设计稿才能进入受控原型验证。
