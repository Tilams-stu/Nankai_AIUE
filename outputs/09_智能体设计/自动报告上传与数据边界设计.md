# 心理健康对话评估智能体自动报告上传与数据边界设计

版本：V1.1（当前方案修订稿）  
日期：2026-07-24  
关联文档：`智能体总体设计方案.md`、`智能体对话流程设计.md`、`危机风险识别与处置规则.md`、`心理评估报告模板设计.md`  
文档目的：说明当前方案取消人工复核闭环后，系统如何在对话结束后后台静默生成报告、自动上传飞书多维表格，并控制学生端反馈、风险资源提示和数据边界。

## 1. 当前口径

本项目最终形态是“无感知测评”。系统在学生完成一次自然语言对话后，不把完整评估报告展示给学生，也不进入人工复核流程，而是在后台静默生成结构化报告，并通过 `report-to-feishu` 工作流自动上传至飞书多维表格。

学生端只保留温和、支持性的对话体验。对于可能存在安全问题的学生，系统只提供学校心理健康中心老师联系电话、校内心理支持渠道等已经确认的资源信息，不承诺自动告警、主动联系第三方或完成危机干预。

## 2. 基本原则

1. 不做人审闭环：报告生成后自动上传飞书，不设置“待人工复核、复核中、确认、驳回”等状态。
2. 不做诊断：报告只能记录本次对话中披露的信息、系统抽取字段、风险线索和信息缺口。
3. 不向学生展示完整报告：学生端不显示内部风险标签、报告字段、证据片段、模型判断过程和飞书记录。
4. 高关注只给资源：出现潜在安全问题时，学生端提供学校心理健康中心老师联系电话等资源信息。
5. 自动流程可追溯：每条飞书记录应包含会话编号、时间、上传状态、报告版本、字段完整性和安全关注状态。
6. 数据最小必要：飞书多维表格只保存项目需要的报告字段，避免默认同步完整原始对话和过度身份信息。

## 3. 自动报告流程

```text
学生完成对话
-> 系统冻结本轮会话字段
-> 自动检查字段完整性、诊断性措辞和安全关注状态
-> 生成后台结构化报告
-> 调用 report-to-feishu 工作流
-> 飞书多维表格新增一条报告记录
-> 学生端只收到温和总结或资源提示
```

该流程不包含人工复核节点。飞书记录用于项目后台留档、后续统计、原型调试和汇报展示，不应被表述为学校已经完成专业评估。

## 4. 飞书字段建议

| 字段 | 含义 | 是否建议上传 |
| --- | --- | --- |
| 会话编号 | 匿名或半匿名会话 ID | 必填 |
| 学号/用户 ID | 与平台身份关联的最小必要标识 | 按项目要求 |
| 上传时间 | 报告写入飞书的时间 | 必填 |
| 主诉摘要 | 用户主要困扰的中性概括 | 必填 |
| 持续时间与变化 | 用户披露的时间线和近期变化 | 建议 |
| 情绪/行为/身体状态 | 已披露的状态表现 | 建议 |
| 功能影响 | 学习、人际、生活等影响 | 建议 |
| 安全关注状态 | 当前对话是否披露需关注线索 | 必填 |
| 学生端资源提示 | 是否已提供心理中心联系方式等资源 | 必填 |
| 信息缺口 | 未询问、拒答或信息冲突内容 | 建议 |
| 报告版本 | 模板和提示词版本 | 必填 |
| 上传状态 | 成功、失败、重试中 | 必填 |

不建议默认上传完整对话原文、详细自伤方法、过度身份信息、未经确认的病因推测、模型隐藏推理和临床诊断式结论。

## 5. 学生端输出边界

学生端可以展示：

1. 对用户表达的简短承接和中性总结。
2. “这不是诊断，也不能替代心理咨询或医疗服务”的边界说明。
3. 与主诉相关的低强度自助建议。
4. 学校心理健康中心老师联系电话等已确认资源。
5. 如有安全线索，建议尽快联系现实中的可信任人员或专业支持。

学生端不展示：

1. 完整后台报告。
2. 内部风险标签 R0/R1/R2/R3/RX。
3. 模型置信度、规则命中细节和证据编号。
4. “你没有风险”“你属于某类疾病”等确定性表达。
5. 飞书多维表格记录内容。

## 6. 风险资源提示规则

当对话出现自伤、自杀、伤害他人、过量服药、无法保证安全、严重失控或安全问题拒答等线索时：

1. 系统暂停普通测评追问，优先确认当前安全。
2. 学生端给出简短、直接的现实支持建议。
3. 提供学校心理健康中心老师联系电话等项目确认资源。
4. 如存在正在发生的危险，建议立即联系身边可信任的人、校内资源或当地紧急服务。
5. 后台报告记录安全关注状态和已提示资源，不写“已完成干预”。

## 7. 数据边界

飞书表格属于项目协作与记录工具，不应被设计成临床诊疗系统。当前阶段建议采用以下边界：

1. 上传字段以结构化摘要为主，减少原始对话全文。
2. 身份字段只保留完成项目记录所需的最小范围。
3. 高敏感风险内容只记录关注状态和必要依据，不展开方法细节。
4. 导出周报、汇报材料或演示材料时默认脱敏。
5. 上传失败需要记录错误状态，但不在学生端暴露技术细节。
6. 后续如要接入真实学生数据，需要先确认隐私、伦理、权限和留存周期。

## 8. 对 NK-GeniOS 原型的影响

原型配置时，重点不再是搭建人工复核队列，而是完成以下闭环：

```text
提示词边界
-> 对话字段抽取
-> 安全关注状态判断
-> 后台报告模板生成
-> report-to-feishu 工作流调用
-> 飞书记录检查
```

建议变量：

| 变量 | 用途 |
| --- | --- |
| `REPORT_MARKDOWN` | 后台报告正文 |
| `SAFETY_STATUS` | 安全关注状态 |
| `RESOURCE_NOTICE` | 学生端是否提示校内心理资源 |
| `UPLOAD_STATUS` | 飞书上传状态 |
| `REPORT_VERSION` | 报告模板版本 |

## 9. 待确认问题

1. 学校心理健康中心老师联系电话、服务时间和展示文案。
2. 飞书多维表格允许保存哪些身份字段和报告字段。
3. 是否需要学生端知情说明中明确“后台会自动生成并上传报告”。
4. 上传失败后的重试、告警和补偿机制。
5. 报告留存周期、访问权限和脱敏规则。

## 10. 汇报表述建议

下一次周报展示中，可以这样说明：

> 当前方案已经从“人工复核闭环”调整为更符合无感知测评定位的“后台静默报告 + 飞书自动上传”。学生在前台只经历自然对话，不直接看到完整评估报告。对话结束后，系统自动整理本轮信息并上传至飞书多维表格，用于项目记录和后续分析。对于可能存在安全问题的学生，系统不声称能够完成危机干预，只提供学校心理健康中心老师联系电话等现实支持资源。
