## 2. 周二组会后的关键口径调整

重点说明：

1. 项目最终不是人工复核系统，而是无感知测评系统。
2. 学生端只进行自然对话，不直接看到完整评估报告。
3. 对话结束后，系统在后台静默生成报告。
4. 报告自动上传到飞书多维表格，用于项目记录、汇总和后续分析。
5. 对于可能存在安全问题的学生，系统只提供学校心理健康中心老师联系电话等资源信息。
6. 系统不承诺诊断、治疗、危机干预、主动告警或第三方联系。

## 3. 智能体设计细节展示

这一部分重点介绍 `outputs/09_智能体设计` 中之前没有展开讲的细节。

### 3.1 总体设计方案

展示要点：

1. 系统定位：高校心理健康对话评估助手。
2. 核心目标：初筛、信息收集、风险提示、后台自动报告。
3. 模块组成：学生端对话、会话状态管理、风险监测、动态追问、报告生成、飞书上传。
4. 设计边界：不是诊断系统，不替代心理咨询或精神科就诊。

### 3.2 对话流程设计

展示要点：

1. 从边界说明开始，先让学生知道系统用途和限制。
2. 先开放式询问最近困扰，再逐步结构化追问。
3. 追问维度包括持续时间、频率强度、情绪状态、睡眠饮食、功能影响、支持系统和安全状态。
4. 每轮只问一个主要问题，避免问卷感。
5. 对话结束后进入后台报告生成和飞书自动上传。

### 3.3 提示词与规则设计

展示要点：

1. 明确智能体角色，不使用“心理咨询师”“医生”等表述。
2. 约束输出语言，避免诊断性、治疗承诺性和污名化表达。
3. 规定每轮回复结构：承接用户表达、提取信息、提出一个关键追问。
4. 规定报告生成格式，保证上传飞书时字段稳定。

### 3.4 危机风险识别与资源提示

展示要点：

1. 风险监测贯穿每一轮对话。
2. 出现自伤、自杀、伤害他人、过量服药、无法保证安全等线索时，普通流程暂停。
3. 系统优先确认当前安全，并提供学校心理健康中心老师联系电话等资源。
4. 系统不声称完成危机干预，也不自动通知第三方。

### 3.5 报告模板与自动上传

展示要点：

1. 报告不直接展示给学生。
2. 报告字段包括主诉、持续时间、状态表现、功能影响、支持系统、安全关注状态、信息缺口和资源提示。
3. 报告生成后调用 `report-to-feishu` 工作流。
4. 飞书多维表格形成一条后台记录。

## 4. NK-GeniOS 智能体完善

展示要点：

1. 已整理 NK-GeniOS 最小化原型制作指南。
2. 原型目标是一条可演示闭环：学生进入智能体 -> 边界说明 -> 开放式表达 -> 结构化追问 -> 安全确认 -> 后台报告生成 -> report-to-feishu -> 飞书记录。
3. 已明确提示词、变量、工作流入参和调试路径。
4. 后续重点是实际配置、模拟测试和字段修正。
