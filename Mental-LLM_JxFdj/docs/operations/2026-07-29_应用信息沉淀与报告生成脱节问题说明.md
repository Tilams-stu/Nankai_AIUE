# 2026-07-29 应用信息沉淀与报告生成脱节问题说明

## 1. 文档目的

本文档只做一件事：把当前应用中已经确认存在的问题、根因判断、基础解决方向和后续方案设计边界写清楚，供后续在新的对话中继续做正式方案设计与代码改造。

本文档**不直接给出最终技术方案实现**，只提供：

1. 当前问题是什么。
2. 为什么会出现这些问题。
3. 哪些结论已经被代码和实际测试证明。
4. 后续应该沿什么方向设计解决方案。

---

## 2. 当前已确认的问题

### 2.1 对话过程中“回答没有真正沉淀”

在真实应用使用过程中，用户已经在当前会话里回答了多个问题，但智能体后续仍然可能表现为：

1. 继续重复追问。
2. 说“关于你的信息仍然是空白的”。
3. 像一个单机问答机一样机械推进，而不是基于已经收集到的信息继续对话。

用户体感上表现为：

- 前面已经聊过很多。
- 但智能体像没有真正“吃进去”这些内容。
- 当前轮的回答没有明显改变后续追问策略。

### 2.2 生成报告时，报告内容与前面对话脱节

当前应用在点击“结束并生成记录”后，虽然能够推进到上传阶段，甚至能够触发飞书写入，但生成出的报告可能存在以下问题：

1. 报告里大量字段仍然是“未询问”“未确认”。
2. 报告没有充分反映前面对话中已经说过的内容。
3. 智能体会声称“之前没有具体聊过你的困扰、状态或近况”。

也就是说，**报告来源与实际对话内容之间存在明显脱节**。

### 2.3 当前系统存在“两个并行的信息收集系统”

应用当前并不是只有一个统一的数据来源，而是同时存在两套并行系统：

1. **前端本地结构化状态系统**
   - 负责本地 transcript
   - 负责本地 assessment fields
   - 负责本地 safety 状态
   - 负责本地 dialogue stage

2. **Genios 智能体自身会话系统**
   - 负责模型自己的自然对话理解
   - 负责模型自己的上下文记忆
   - 负责模型自己生成报告并调用工作流

这两套系统目前没有被统一成单一真相源。

## 3. 已确认的事实依据

以下结论不是猜测，而是结合现有代码结构和实际运行结果确认出来的。

### 3.1 前端本地其实在持续收集结构化信息

前端本地状态链路已经存在，并且确实在运行：

- `src/app/sessionRuntime.js`
- `src/services/assessmentStateService.ts`
- `src/services/safetyRuleService.ts`
- `src/services/dialogueStageService.ts`

其中关键事实是：

1. 用户每轮输入会进入 `MentalSessionRuntime.ingestUserTurn(...)`。
2. 本地 transcript 会被记录。
3. assessment fields 会依据关键词和阶段进行更新。
4. safety 状态会被更新。
5. dialogue stage 会被推进。

因此，“应用前端完全没有记录信息”这件事并不成立。  
**前端本地其实有在记录。**

### 3.2 发送给 Genios 的并不是“本地已确认状态”，而主要只是当前这轮输入

在当前聊天实现中，实际发给 Genios 的请求位于：

- `src/app/chatRuntime.js`

当前发送主体是：

```js
additional_messages: [{ role: 'user', content: text, content_type: 'text' }]
```

这说明：

1. 本地收集到的结构化字段并没有作为每轮标准上下文同步给智能体。
2. 智能体主要靠自己的会话记忆来理解前面聊过什么。
3. 本地 assessment / safety / dialogue stage 并没有成为模型稳定可见的决策输入。

### 3.3 本地已经有“可生成正式报告 payload”的能力

本地报告链路已经存在：

- `src/app/reportDraftRuntime.js`
- `src/services/reportDraftService.ts`
- `src/services/reportTemplateService.ts`
- `src/services/workflowPayloadService.ts`

这条链路能够从本地状态中读取：

1. `session`
2. `assessment`
3. `transcript`
4. `safety`
5. `upload`

并生成稳定的：

- `REPORT_MARKDOWN`
- `SEVERITY_LEVEL`
- `STUDENT_ID`
- `TIME`

也就是说，**本地本来就具备“基于真实已收集状态生成报告”的能力**。

### 3.4 当前 `agent_internal` 路径下，最终报告主要仍由智能体自己生成

当前“结束并生成记录”的逻辑位于：

- `src/app/pageRuntime.js`

在 `agent_internal` 模式下，当前收尾方式本质上是：

1. 给智能体发一条隐藏的收尾指令。
2. 让智能体根据它自己的上下文“生成后台留档报告”。
3. 再由智能体自己调用 `report-to-feishu`。

这意味着：

1. 前端本地状态不是最终报告的唯一来源。
2. 智能体自己的记忆好不好，直接影响最终报告内容。
3. 一旦模型上下文没有稳定吸收前面对话，本地已经收集的信息也无法自动进入最终报告。

### 3.5 飞书写入链路本身已经打通

这部分已经被后续实际测试证明：

1. 工作流调用链路可以成功触发。
2. 飞书多维表格可以真正新增数据。
3. 应用、Genios、工作流、飞书之间的基础技术通路已经存在。

因此，当前问题的重点**不是“能不能写飞书”**，而是：

> 写进飞书的那份报告，到底是依据谁生成的。

## 4. 根因分析

### 4.1 根因一：存在两个信息来源，但没有统一真相源

当前系统最大的问题不是“没有记录”，而是：

**记录来源被拆成了两套，但最终没有统一。**

具体来说：

1. 前端本地记录了一套结构化状态。
2. Genios 智能体又维护了一套自己的会话理解。
3. 最终报告更多依赖智能体自己的会话理解。
4. 但用户实际观察和交互的是前端本地状态。

这就造成了典型的“状态分裂”：

- 用户觉得已经回答过了。
- 前端本地也可能真的记住了。
- 但智能体未必同步知道。
- 最后报告又由智能体生成，所以报告和真实对话脱节。

### 4.2 根因二：本地结构化信息没有稳定注入模型上下文

提示词要求智能体：

1. 依据已确认字段继续推进。
2. 不要重复提问。
3. 在信息收集完成后生成结构化报告。

但这些要求只有在一个前提成立时才有效：

> 模型每轮都能稳定看到“已确认了哪些字段，未确认了哪些字段”。

当前这个前提并不成立。

因此模型实际表现会退化成：

- 只根据最近几轮自然语言记忆继续聊天
- 一旦记忆不稳，就重复问
- 一旦收尾时上下文不完整，就生成空白/缺失报告

### 4.3 根因三：收尾动作仍然依赖模型理解，而不是确定性流程

当前“结束并生成记录”虽然已经做成按钮，但在 `agent_internal` 路径下，本质仍然是：

1. 发一条隐藏自然语言指令
2. 希望模型理解“现在该生成报告并调用工作流”

这不是一个完全确定性的业务流程，而仍然是“再聊一句”。

这种方式的风险是：

1. 模型可能理解偏差。
2. 模型可能只生成自然语言结束语。
3. 模型可能基于不完整记忆生成报告。

### 4.4 根因四：会话连续性对代理内存有隐性依赖

本地代理当前通过内存维护 conversation 映射。  
这意味着一旦代理重启、端口变化、映射丢失，智能体就可能出现会话断裂。

即使这不是当前最核心的问题，它也会加剧“前面明明聊过，但后面像没聊过”的现象。

---

## 5. 这个问题为什么会表现成“单机问答机”

因为当前系统里，智能体在问下一题时并没有一个稳定的“结构化会话状态”输入。

它看到的更多是：

1. 当前这一轮用户说了什么。
2. 它自己上下文窗口里残留了多少历史。
3. 提示词要求它“尽量像已经理解了”继续聊。

这会导致一个非常典型的失败模式：

1. 模型每轮都能生成合理追问。
2. 但追问不一定真正建立在已确认字段之上。
3. 回答看起来流畅。
4. 结构上却没有真正“累积”。

用户就会感觉：

- 它一直在问
- 但回答并没有改变它的内部状态
- 像个单机问问题机器

## 6. 基础解决方向

下面这些是“方向性结论”，不是最终实现细节。

### 6.1 解决方向一：确立单一真相源

后续方案必须明确：

> 最终报告到底以谁为准。

当前最合理的方向是：

**以本地结构化状态作为报告生成的唯一正式来源。**

原因：

1. 本地已经有 `transcript + assessment + safety + stage`。
2. 本地已经有生成报告 payload 的能力。
3. 本地状态比模型自然语言记忆更稳定、可检验、可追踪。

### 6.2 解决方向二：让智能体聊天时能够“看见”本地已确认状态

如果还希望智能体继续负责自然对话，那么每轮应该把本地状态摘要同步给智能体，例如：

1. 已确认主诉
2. 已确认持续时间
3. 已确认情绪/睡眠/功能影响
4. 当前安全状态
5. 下一步优先追问字段
6. 不要重复问的字段列表

也就是说，模型不能只看用户这轮原话，还要看“会话结构化摘要”。

### 6.3 解决方向三：收尾动作改成确定性流程，而不是自然语言请求

“结束并生成记录”后续应尽量变成：

1. 检查本地必填项完成度
2. 检查安全确认是否完成
3. 若未完成，拦截并要求补齐
4. 若满足条件，直接生成本地正式报告
5. 再调用工作流上传飞书

而不是：

1. 给模型发一句隐藏提示
2. 希望它“自己理解并完成”

### 6.4 解决方向四：把“聊天职责”和“报告职责”解耦

后续架构设计应该明确：

1. **智能体负责聊天与表达**
2. **本地状态负责信息沉淀**
3. **报告生成负责把已沉淀状态组织成稳定报告**
4. **工作流负责上传**

这样每一层职责单一，问题也更容易排查。

## 7. 推荐的后续设计顺序

### P0：先解决报告与信息沉淀脱节

1. 不再让 `agent_internal` 路径下的最终报告完全依赖智能体临场生成。
2. 把本地 `reportDraftRuntime` 提升为正式报告来源。
3. 保留工作流上传飞书，但上传内容来自本地稳定 payload。

### P0：再解决“回答没有改变后续追问”

1. 设计“本地结构化摘要 -> 模型隐藏上下文”的注入机制。
2. 每轮同步“已确认字段 / 未确认字段 / 下一步优先项”。
3. 让智能体后续提问真正基于结构化状态推进。

### P1：提升会话连续性和可观测性

1. 增加状态调试面板，直接看到当前 assessment fields。
2. 增加会话快照恢复能力。
3. 更清晰地区分“模型认为已确认”和“系统正式已确认”。

---

## 8. 不建议继续沿用的做法

以下做法后续不应继续作为正式方案依赖：

1. 仅靠提示词要求模型“不重复提问”。
2. 仅靠模型自然语言记忆来生成最终报告。
3. 在收尾阶段再给模型补一条自然语言隐藏指令，希望它自己完成报告生成。
4. 在没有统一真相源的情况下，让前端状态和模型状态并行存在但互不同步。

---

## 9. 后续方案设计时必须回答的问题

在新的设计对话中，需要明确回答以下问题：

1. 最终报告的唯一正式来源是前端本地状态，还是 Genios 智能体状态？
2. 如果以前端本地状态为主，如何与 Genios 智能体的工作流调用对接？
3. 每轮要同步给模型的隐藏结构化上下文长什么样？
4. 收尾动作的最小必填条件是什么？
5. 安全确认、主诉、持续时间、功能影响等字段到什么程度允许生成正式报告？
6. 工作流上传前是否需要对本地 payload 做字段完整性校验？

---

## 10. 当前阶段结论

当前应用的核心问题不是“不能写飞书”，而是：

> **本地已经收集到的信息，没有稳定成为最终报告和后续对话推进的统一依据。**

它的本质是：

1. 信息沉淀链路存在
2. 聊天链路存在
3. 上传链路存在
4. 但三者没有被统一成一条单一、可控、可验证的正式业务链路

因此后续方案设计的主线应当是：

> **统一信息来源，稳定同步聊天上下文，收尾时使用确定性的本地报告生成 + 工作流上传。**
