### 1.2 已有代码（实现层）

| 文件 | 作用 | 问题 |
| --- | --- | --- |
| `index.html`（~1300 行） | 聊天 UI、3D 模型、GAD-7 视图、配置、API 调用全混在一起 | 单文件过大，难维护 |

| `manifest.json` | PWA 配置 | 待迁移 |

当前前端已能：
- 通过 `proxy_server.py` 调用 NK-GeniOS 对话 API（流式）
- 展示 3D 小狮子形象 + 聊天气泡
- 切换 GAD-7 专用 Bot
- 本地存储 API Key / Bot ID / 用户信息

当前前端尚未实现：
- 项目设计的「开放式主诉 + 结构化追问 + 安全确认」流程（依赖 NK-GeniOS Agent 配置）
- 后台报告静默生成与飞书上传的前端感知（上传在 Agent 侧完成）
- 学生端边界声明、危机资源提示的配置化
- 视图/逻辑/服务分层
- 领域模型（会话状态、风险标签、报告状态）

### 1.3 核心口径（开发时必须遵守）

1. **系统定位**：高校心理健康对话评估助手，不是医生/咨询师/诊断系统。
2. **学生端**：只展示温和对话 + 简短总结 + 资源提示；**不展示**完整报告、R0-R3/RX 标签、飞书记录。
3. **报告**：对话结束后后台静默生成 → 调用 `report-to-feishu` → 写入飞书多维表格。
4. **无人工复核闭环**：报告状态为「自动上传待留档」，不设复核队列。
5. **安全表达**：不能写「无风险/确诊/排除」；只能写「当前对话未披露明确即时风险」等。
6. **工作流入参**（固定 4 个）：`input`、`SEVERITY_LEVEL`、`Student_ID`、`time`。

## 2. 总体架构目标

```text
┌─────────────────────────────────────────────────────────┐
│  学生端 (Mental-LLM_JxFdj)                               │
│  index.html → components → services → domain            │
└────────────────────┬────────────────────────────────────┘
                     │ POST /api/chat (SSE)
                     ▼
┌─────────────────────────────────────────────────────────┐
│  proxy_server.py (server/)                               │
│  创建/复用 Conversation → chat_query 流式转发             │
└────────────────────┬────────────────────────────────────┘
                     │ NK-GeniOS API
                     ▼
┌─────────────────────────────────────────────────────────┐
│  NK-GeniOS Agent「Mental Wellbeing 初筛助手」             │
│  提示词 + 变量 + report-to-feishu 工作流                  │
└────────────────────┬────────────────────────────────────┘
                     │ create_records
                     ▼
┌─────────────────────────────────────────────────────────┐
│  飞书多维表格（后台报告留档）                              │
└─────────────────────────────────────────────────────────┘
```

**双轨并行**：
- **轨道 A（NK-GeniOS 平台）**：配置 Agent、变量、工作流——按 `NK-GeniOS最小化原型制作指南.md` 操作。
- **轨道 B（本地代码）**：工程重构 + 前端对接 + 领域模型 + 测试——本计划主体。

## 8. 风险与规避

| 风险 | 影响 | 规避 |
| --- | --- | --- |
| 不引入构建工具导致 ES Module 兼容性 | 阶段 4 拆分后浏览器报错 | 使用 IIFE + window 命名空间，或 `<script type="module">` 仅现代浏览器 |
| index.html 拆分引入路径错误 | 页面白屏 | 每步对比 legacy 备份；smoke test 必须通过才进下一阶段 |
| Agent 回复含完整报告展示给学生 | 违反数据边界 | 阶段 5B/7 的前端报告过滤 |
| 飞书工作流权限/字段变更 | 上传失败 | 不改工作流结构；排查清单写入 agent_integration.md |
| 口径不一致（人工复核 vs 自动上传） | 报告状态字段混乱 | 统一使用「自动上传待留档」，废弃「待人工复核」 |
| 危机漏报 | 安全事故 | Agent 提示词为主；前端 detectRiskLevel 为辅助；T06/T07 必测 |

## 11. 每次 Codex 会话推荐工作流

按 `project-lifecycle` 技能：

1. **Roadmap**：确认本次要执行的阶段编号 → 阅读本文对应章节
2. **Development**：只改对应文件，最小 diff
3. **Testing**：跑 smoke_check + 相关 manual_cases
4. **Progress**：在 `progress/YYYY-MM-DD_log.md` 留档

**示例单次会话**：

```text
请执行《完整代码开发计划》阶段 3。
完成后运行 smoke_check，并在 progress/ 留档。
不要执行其他阶段。
```

## 13. 最终 MVP 验收标准

1. 学生打开页面 → 看到边界说明 → 自然对话 → 不看到完整报告。
2. 对话结束 → Agent 生成报告 → 飞书新增一条记录。
3. 含蓄/明确风险表达 → Agent 安全澄清 + 前端资源提示。
4. 代码目录清晰，docs/tests/progress 齐全。
5. 12 条 manual_cases 全部通过。
6. 组会可演示完整闭环并说明工程结构。
