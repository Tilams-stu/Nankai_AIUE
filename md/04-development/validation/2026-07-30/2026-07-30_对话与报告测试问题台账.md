# 对话与报告测试问题台账

日期：2026-07-30  
状态：持续更新中

## 使用规则

- 每条测试记录必须区分“学生端智能体回复”和“飞书后台记录”，避免混淆可见范围。
- 每次测试从新会话开始，记录测试学号、输入顺序、智能体完整回复、飞书结果和结论。
- 新问题按优先级记录；修复后保留原记录，并补充复测结果，不删除历史。

## 当前结论（先读这里）

当前系统的主要缺陷不是若干孤立话术，而是底层对话策略仍以“补齐测评字段”为中心。学生给出明确任务、边界或风险语义时，Agent 通常能完成单轮回应；输入变为开放叙述、并列议题或跨轮补充后，系统便回落为“模板共情 + 情绪/时长/功能影响追问”。

后续改造应以本地逻辑为主：持久化互动模式、传递有顺序的完整最近对话、限制跨话题字段追问、用本地状态机完成收尾和报告提交。NK-GeniOS 平台提示词与工作流绑定保持稳定，除非涉及安全底线或四字段接口。

## 设计根因与本地迭代约束

### 已确认的设计根因

当前实现本质上仍是“字段采集优先”的访谈流程：本地根据 `missingFields`、`targetField` 和 `nextQuestionPriority` 决定下一轮缺什么，再让 Agent 用较温和的话术追问。因此它会在学生正谈家庭沟通时，为补充“情绪状态”或“功能影响”而主动换题，例如“抛开跟家人怎么说这件事……”。

目标体验应调整为“对话优先，测评旁路发生”：

```text
学生当前想说什么
-> Agent 围绕同一话题自然回应或轻度展开
-> 本地从学生自然表达中静默提取评估信息
-> 信息足够后由本地形成非诊断性报告并决定收束/提交
```

而不是：

```text
缺少哪些测评字段
-> 本地指定 targetField
-> Agent 追问该字段
```

BUG-012、BUG-013、BUG-014 是该设计根因的不同表现，不应只通过逐句修改 Agent 话术处理。

### 对话测试结论与停止条件（2026-07-30）

当前黑盒测试已经形成足够重复的证据：当学生输入含有明确任务、明确边界或明确风险语义时，Agent 往往可以完成单轮回应；但当输入是开放叙述、并列困扰、需要跨轮记忆的补充，或学生没有直接指定要做什么时，系统会稳定回落为“通用共情模板 + 情绪/时长/功能影响字段追问”。跨轮承诺（如“不分析”）和对话主题也不能可靠保留。

因此，不再投入时间用同类开放式话术重复验证 BUG-012、BUG-013、BUG-014、BUG-015、BUG-027。后续测试只保留两类：

1. 高风险或高权限流程：安全分流、同意/拒绝上传、短会话结束、报告调用、数据更正和隐私边界。
2. 本地改造完成后的针对性回归：互动模式持久化、完整的最近对话序列、话题守卫和报告状态机。

### 本地上下文断点

- `conversationContextService.ts` 已生成 `recentAgentEvidence`，但 `proxy_server.py` 组装平台请求时只消费用户原话、字段摘要和策略，未将先前 Agent 回复按顺序传给平台。
- `SessionState` 不存在 `free_chat`、`assessment_paused` 等持久化互动偏好；学生说“先别分析”只会影响当前一轮，下一轮仍会因缺字段回到 `clarify`。
- 收束请求把完整字段摘要、未确认字段、测评策略和工具 payload 一并传给 Agent，容易让模型把当前轮当作“继续总结/补字段”的普通对话，而不是专门的工具交接。

### 平台与本地的变更边界

NK-GeniOS 平台提示词或工具配置的修改需要重新发布并人工审核。后续迭代遵循“本地优先”原则：除非涉及安全底线、工作流工具绑定或四字段接口，否则不为日常对话行为反复修改平台提示词。

| 层级 | 保持稳定 / 负责内容 | 后续优先改动位置 |
| --- | --- | --- |
| NK-GeniOS 平台 | 安全底线、`report-to-feishu-yhx` 工具绑定、工作流四字段接口 | 仅集中进行必要的审核版更新 |
| 本地会话策略 | 互动模式、追问许可、收束时机、重复追问保护 | `ConversationPolicy`、`SessionState` |
| 本地上下文代理 | 近期对话顺序、当前话题、隐藏工具交接请求 | `proxy_server.py`、`conversationContextService.ts` |
| 本地测评与报告 | 从自然表达提取字段、报告生成、上传状态与失败反馈 | `AssessmentState`、报告草稿与上传运行时 |

### 后续本地改造方向

1. 增加可持久化的互动模式：至少区分 `assessment`、`free_chat`、`safety`、`closing`；学生明确要求“随便聊”“先别分析”后进入 `free_chat`，直到学生主动恢复或出现安全优先信号。
2. 在 `free_chat` 模式中，不向 Agent 暴露 `missingFields`、`targetField`、`nextQuestionPriority`；只传当前主题、近期按时间排序的用户与 Agent 对话，以及“具体承接、不追问”的本地指令。
3. 普通模式也应将“字段未收集”降为本地旁路信息。Agent 只能围绕学生正在谈的主题提出一个自然、可拒绝的问题，不能为了补字段主动切题。
4. 为最终上报使用独立、精简的工具交接上下文，避免与 `responseMode: summarize`、完整缺口表和普通对话规则混在同一请求中。
5. 在本地回复守卫中增加自由聊天保护：若学生已设定“不要分析”边界，检测到新的字段式追问时要求 Agent 重生成具体承接，而不是仅输出“我在听”。

## 后续回归清单

在本地改造完成前，不继续进行开放式对话的黑盒测试。改造后按以下顺序回归：

1. **结束与报告链路**：重启本地代理后，验证明确结束、短会话结束、拒答安全确认三种情况的本地结果、`report-to-feishu-yhx` 调用和飞书单条 upsert。
2. **同意、隐私与数据权利**：验证不上传、核对摘要、纠正旧信息、第三方信息和虚构内容均不会被错误写入学生报告。
3. **安全路由**：验证本人即时风险、既往风险但当前否认、身体不适、第三方求助四类输入各自进入正确的现实支持分流。
4. **对话体验**：验证 `free_chat` / `assessment` / `closing` 模式切换、跨轮边界记忆、并列话题承接和“仅具体承接、不追问”的回退守卫。
