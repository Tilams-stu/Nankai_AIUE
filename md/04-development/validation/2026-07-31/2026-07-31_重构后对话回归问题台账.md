### REG-001：有效回复被兜底文本覆盖并重复显示

| 项目 | 记录 |
|---|---|
| 测试日期 | 2026-07-31 |
| 测试场景 | 围绕“经常在关键时刻软脚”的困扰进行自然对话 |
| 触发内容 | 用户先描述相关经历和上下文，随后询问“你觉得我怎么办比较好”，并继续补充确认 |
| 优先级 | P1：核心对话回复不可稳定呈现，直接影响测试体验 |
| 证据 | `C:/Users/Administrator/AppData/Local/Temp/codex-clipboard-01035cbd-fa70-4ef4-8074-ef9de7a60841.png` |
| 关联历史问题 | 暂无直接关联；本条按重构后新回归问题记录 |

#### 预期结果

- 用户提出“你觉得我怎么办比较好”后，应保留并显示智能体已经生成的完整、相关回复。
- 一次用户输入对应一次最终的助手消息，不应被后续兜底文本覆盖。
- 如果流式响应失败，兜底文本只能在确实没有可用回复时显示，不能覆盖已经收到的有效内容。
- 后续用户发送“？”或重述上一问题时，应基于当前上下文回应，不能机械重复同一句话。

#### 实际结果

- 用户看到智能体原本有一串相对完整的回复内容。
- 随后该内容突然被刷新掉，页面最终显示为：

  > 我听到了，你可以继续说你最想说的部分。

- 该固定回复随后重复出现多次；用户发送“？”以及“我刚才说我怎么办比较好”后，仍然得到同一句回复。
- 当前无法仅凭页面判断：是有效流式响应被前端覆盖、旧请求的兜底回调晚到，还是同一消息被重复提交。

#### 2026-08-01 复测证据

本轮围绕“关键时刻软脚”进行新会话测试。用户输入包含主诉、持续时间、学习影响和睡眠影响，并要求先针对当前内容回应，不要像问卷一样逐项追问。

智能体最先生成的可见回复内容为：

> 谢谢你把这些说得这么清楚。你描述的这种“平时准备时觉得能做到，但关键时刻突然软脚”的感觉，我想很多人都能感同身受——那种落差确实让人沮丧，尤其事后还要反复回想、自责，连晚上睡觉都受影响，一个多月下来真的挺磨人的。你愿意先把这件事摊开来讲，而不是急着找解决方案，这个节奏本身就很好。如果有什么你想继续展开的，随时可以说。

这段回复本身暂未发现明显的对话策略问题：它回应了具体主诉，承接了持续时间、学习/睡眠影响，没有重新索要字段，也没有强行结束对话。

但用户来不及复制该回复，页面随后刷新出另一段内容，用户感觉像是“上一次回答的后续”。本轮尚未取得刷新后第二段回复的完整文本，因此暂时不能判断它是：

1. 同一轮流式回复被回复守卫或兜底逻辑替换；
2. 旧请求的异步结果晚到后写回当前页面；
3. 页面刷新后从 `sessionStorage` 恢复了上一会话的 transcript；
4. 同一用户输入被发送了不止一次。

本轮新增观察：

- 前一段有效回复能够正常生成，说明问题不一定发生在 Agent 首次生成阶段；
- 异常发生在回复生成后的前台显示或会话恢复阶段；
- 若第二段内容确实来自上一会话，则还需要单独建立“跨会话内容串入”回归问题；目前先作为 `REG-001` 的关联证据保留。

#### 初步定位方向

1. 检查 `chatRuntime.js` 中流式消息的创建、追加、完成和失败回调是否可能同时执行。
2. 检查请求超时、空响应或异常回退逻辑是否会覆盖已经存在的 assistant 消息。
3. 检查消息 ID、请求 ID 或会话轮次是否被复用，导致旧请求回写到新消息。
4. 检查发送按钮、回车发送和重试逻辑是否可能对同一用户输入触发多次请求。
5. 检查前端在收到流式结束事件后是否又执行了一次通用“我在听”兜底渲染。
6. 对照代理日志确认同一轮输入是否产生一次还是多次 `/api/chat` 请求，以及上游是否实际返回了完整答案。
7. 检查页面刷新后 `sessionStorage` 中的 `mental_llm_session_snapshot_v2` 是否仍为上一会话，以及登录后是否真正执行了新会话重置。
8. 比较刷新前后的 transcript `sessionId`、最后一条用户输入和最后一条 Agent 回复，确认刷新内容是否来自当前会话。

#### 当前状态

已由两轮用户实测观察到同类“有效回复随后被替换/刷新”的现象。2026-08-01 已完成前端回复提交逻辑修复，等待真实对话复测确认。

#### 2026-08-01 定位与修复结果

- 根因已确认：`src/app/chatRuntime.js` 原先在首轮流式响应期间持续更新同一个助手气泡；响应守卫判定需要修复时，又会清空该气泡、发起第二次请求并继续写入，修复失败后还会用固定兜底句再次覆盖。因此用户会看到“先出现正常回复，随后刷新成另一段内容”。
- 修复方式：首轮响应和守卫修复响应均只在后台累积；完成守卫判定后选择合规回复、修复回复或兜底文本，最后只向可见气泡提交一次。空响应也会稳定落到兜底文本，不再让气泡停留在加载状态。
- 影响边界：只调整前端可见回复的提交时机，保留 Agent 请求、响应守卫、会话 transcript 记录和自动报告更新流程；隐藏的自动报告请求不创建可见气泡。
- 自动化证据：`npm test` 通过 44 个子测试；新增回归断言确认守卫重试场景气泡只更新一次，并新增多段流式片段只提交一次的测试。`npm run typecheck`、`npm run build`、`npm run smoke` 和 `npm run validate:local` 均通过。
- 真实复测要求：重新进行一次包含主诉、持续时间和影响描述的自然对话，确认可见气泡从加载态直接稳定为最终回复，且同一条助手消息不再出现第二次刷新；同时观察代理日志中该轮是否仍只产生预期的可见请求与隐藏报告请求。

#### 复测要求

修复后使用新会话至少验证以下三种情况：

1. 普通长输入：完整回复不会被兜底句覆盖。
2. 流式响应较慢：等待期间不会产生重复 assistant 消息。
3. 请求异常或空响应：只显示一次明确的失败/兜底反馈，后续输入可以恢复正常上下文。
4. 页面刷新后：只恢复当前会话的 transcript，不出现上一会话的回复或用户输入。
