# 核心闭环答辩前对话验证方案

日期：2026-08-01  
目标：在答辩前只验证项目最核心的可用闭环，不扩展无关功能。

## 一、最小目标

本轮只需要证明以下链路成立：

```text
学生自然表达困扰
-> 智能体围绕当前话题正常交流
-> 本地从自然表达中沉淀主诉和相关信息
-> 后台自动生成或更新非诊断报告
-> 学生不需要点击“生成报告”
-> 报告更新后对话仍可继续
```

“本地 payload 已生成”不等于“飞书已经写入”。如果最终报告以飞书记录为准，还必须单独确认 Agent 内部工作流调用和飞书行记录。

## 二、测试前准备

1. 使用新的 synthetic 学号和新会话，避免旧状态干扰。
2. 记录测试版本、开始时间、学号后缀和当前 Agent。
3. 确认代理服务、前端服务和 `/api/workflow/status` 正常。
4. 确认工作流模式为 `agent_internal`，并清楚这是 Agent 内部交接路径。
5. 打开后台审计记录入口：`/api/workflow/audit-records`，测试前记录已有条数。
6. 每个关键轮次等待当前回复完全结束，再发送下一条消息。
7. 每个会话保留学生端截图，并记录审计记录、Agent 调用或飞书行的时间。

## 三、必测对话场景

### A0：普通问候不应创建空报告

示例输入：

```text
你好，今天想随便聊聊。
```

检查：

- 智能体正常回应，不直接开始字段式询问；
- 不显示完整后台报告；
- 不产生空的报告更新或空审计记录。

通过条件：普通问候和闲聊不会污染主诉，也不会创建空报告。

### A1：首次出现主诉时自动创建报告

示例输入：

```text
最近论文压力很大，尤其是在关键时候总感觉自己会“软脚”，明明准备过，真正要做的时候却发挥不出来。
```

检查：

- 智能体先回应学生正在表达的困扰，不立即索要完整字段；
- 学生端只看到自然回复，不看到报告正文或内部字段；
- 本地状态出现主诉证据；
- 后台出现第一次自动报告 payload 或审计记录；
- 不需要点击结束或生成报告按钮。

通过条件：首次有意义的本人陈述能够触发自动创建记录。

### A2：补充相关信息时更新同一份报告

在 A1 的同一会话中继续表达，例如：

```text
这种情况大概持续一个多月了，平时准备的时候还好，但一到真正需要表现的时候就会紧张、拖延，晚上也容易睡不好。
```

检查：

- 智能体结合上一轮内容回应，不重新开始访谈；
- 后台报告中的持续时间、情绪、睡眠或功能影响等信息出现更新；
- `sessionId` 保持一致；
- 如果已经存在对应记录，应走更新而不是无条件创建新记录；
- 学生端仍然可以继续对话。

通过条件：同一会话的新增信息会更新原报告，不产生重复的独立记录。

### A3：报告更新后继续自然交流

在 A2 后继续询问：

```text
那你觉得我怎么办比较好？
```

检查：

- 智能体先回答当前求助问题；
- 不立即切回“持续多久、影响多大”等字段追问；
- 不因为后台已经更新报告而自动结束对话；
- 不出现“我听到了，你可以继续说你最想说的部分”这类与当前问题无关的兜底句；
- 同一轮只出现一条最终助手消息，不被后续内容覆盖或重复。

通过条件：报告旁路更新不打断前台交流。

### A4：用户继续补充或更正信息时再次更新

示例输入：

```text
我刚才说睡不好不完全准确，主要是入睡会拖很久，睡着以后不一定会醒；真正影响最大的是关键场合容易退缩。
```

检查：

- 新信息覆盖或补充旧信息，而不是简单追加互相矛盾的结论；
- 报告中的睡眠和功能影响字段分别保存；
- 后台更新时间发生变化；
- 学生可以继续解释，不被强制总结或结束。

通过条件：报告能够随会话中的新证据更新，并保留可解释的最新状态。

### A5：不主动生成报告也能留下记录

在信息已经足够但用户不点击结束时，继续发送一条自然表达：

```text
我暂时也没有别的想补充了，不过还想再听听你的建议。
```

检查：

- 智能体先回应当前表达；
- 后台已经存在至少一条有效报告记录；
- 不要求用户说“生成报告”；
- 对话仍然可以继续。

通过条件：报告生成是后台行为，不由学生控制，也不依赖明确的报告按钮。

### A6：结束按钮触发最终更新

在已有正常对话记录后点击结束按钮。

检查：

- 如果安全确认尚未完成，先完成一次安全确认；
- 结束操作触发最终报告更新；
- 同一会话不重复创建多条记录；
- 学生端只显示简短的记录状态，不展示后台报告正文；
- 服务端或审计记录中能看到最终 payload。

通过条件：结束按钮是兜底路径，不是正常报告生成的唯一入口。

### A7：回复完整性和兜底覆盖回归

这是当前必须优先验证的 `REG-001`。

操作：

1. 新建会话，围绕“关键时刻软脚”进行至少 3～5 轮交流；
2. 发送“你觉得我怎么办比较好？”；
3. 等待回复完全结束后，再发送“？”和“我刚才说我怎么办比较好”；
4. 观察每一轮页面消息和代理日志。

检查：

- 先收到的完整回复不会被固定兜底句覆盖；
- 同一用户输入不会触发两条最终助手消息；
- 慢响应、流式结束和回复守卫不会互相覆盖；
- 异常时最多出现一次明确兜底反馈，下一轮能恢复正常。

通过条件：`REG-001` 不再复现。否则不能把前台对话主链路标记为通过。

## 四、后台证据必须分层记录

每个核心场景都要分别记录以下四层结果：

| 层级 | 要确认的内容 | 证据 |
|---|---|---|
| 学生端 | 回复自然、没有完整报告、没有重复覆盖 | 截图、对话文本 |
| 本地状态 | 主诉和相关字段发生变化 | 会话快照或调试状态 |
| 本地报告通路 | 自动 payload 已生成并交给 Agent | `/api/workflow/audit-records`、`sessionId`、`payloadHash` |
| 外部工作流 | Agent 实际调用报告工作流并写入飞书 | Agent 调用日志、飞书行 ID、更新时间 |

只拿到本地审计记录时，结论应写成：

> 本地已确认报告 payload 自动生成并进入 Agent 内部提交路径，真实飞书写入仍待外部证据确认。

拿到飞书行创建或更新时间后，才可以写成：

> 已确认同一会话的后台报告能够自动创建，并在新增信息后更新已有记录。

## 五、最小通过标准

答辩前至少完成 A0～A6，并满足：

- A0 通过：闲聊不产生空报告；
- A1 通过：出现主诉后自动创建报告；
- A2 通过：新增信息更新同一会话报告；
- A3 通过：报告更新不打断自然对话；
- A4 通过：更正信息能够更新字段；
- A5 通过：不点击生成报告也有后台记录；
- A6 通过：结束按钮能够完成最终更新；
- A7 不得出现 `REG-001`；
- 学生端不展示完整后台报告、内部风险标签或 payload。

如果暂时无法确认真实飞书写入，仍可以完成本地闭环演示，但答辩中必须把“本地自动生成并交给 Agent”和“飞书最终写入”分开表述。

## 六、暂时不作为答辩前主线的内容

在以上闭环通过前，不再优先投入时间处理：

- 所有视觉细节和状态页趋势图；
- 全部量表的完整产品化；
- 多人并发和长期部署；
- 临床有效性、诊断准确性和完整危机干预能力；
- 所有旧台账问题的重新黑盒复测。

安全高风险、隐私和第三方内容仍应保留最基本的保护性检查，但它们是安全边界验证，不是本次“主诉到后台报告自动更新”核心闭环的主要证明。
