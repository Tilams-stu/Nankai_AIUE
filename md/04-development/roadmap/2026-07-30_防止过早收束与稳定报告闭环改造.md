# 防止过早收束与稳定报告闭环改造

## 问题与目标

当前学生回答了一个澄清问题的简短答案（例如“这几天吧”）后，Agent 可能直接说“今天先到这里”，即使本地策略仍要求围绕功能影响继续一个澄清问题。这不是信息充分判定的预期行为，而是平台模型把单轮简短回答误判为结束信号，且浏览器端缺少执行兜底。

本次改造目标：

1. 只有学生明确表达结束意图，或本地 `responseMode` 为 `summarize`/`close` 时，Agent 才能收束。
2. 对上一轮问题的短回答视为正常继续，不得据此自行结束。
3. 当本地策略为 `clarify` 却收到明显的提前收束文案时，浏览器端进行一次隐藏的纠偏续答请求，不把中断体验留给学生。
4. 保持报告只在本地明确的结束判定下生成；核对 Agent 文案触发逻辑，避免随机提前生成或漏生成。

## 技术方案

### 1. 平台提示词约束

影响文件：`files/智能体提示词.md`

- 增加“短回答并不等于结束”的明确规则。
- 为 `clarify` 增加硬约束：必须承接并只问 `targetField` 对应的一个问题；禁止使用“今天先到这里”“之后再聊”等收束语。
- 为 `respond` 增加“不可主动宣告会话结束”的约束。
- 仅在 `summarize`、`close` 或学生明确表达结束意图时允许总结/收束。

该文件继续作为 NK-GeniOS 平台提示词的唯一复制来源，修改后需要整体替换并重新发布。

### 2. 本地提前收束识别与一次纠偏

影响文件：

- `Mental-LLM_JxFdj/src/app/chatRuntime.js`
- 新增 `Mental-LLM_JxFdj/src/services/earlyClosureGuardService.ts`
- 新增或扩展对应 runtime 构建产物

数据流：

```text
用户输入 -> AssessmentState/ConversationPolicy -> local_context_packet
  -> Agent 首次回复
  -> earlyClosureGuard 检查 responseMode 与回复语义
  -> 若 clarify/safety_check 被提前收束：隐藏纠偏指令 -> Agent 续答一次 -> 学生看到修正后的回复
```

守卫仅对 `clarify` 和 `safety_check` 生效，并限制为每个用户回合最多一次，避免循环请求。不会为 `summarize`、`close` 和 `safety_route` 覆盖 Agent 输出。

### 3. 报告生成条件核对

影响文件：

- `Mental-LLM_JxFdj/src/app/uploadRuntime.js`
- `Mental-LLM_JxFdj/src/app/chatRuntime.js`

- 保留“学生明确结束意图”及本地 `ready_to_close` 的报告触发。
- 移除或收紧依赖 Agent 自由文本中结束短语的触发，避免 Agent 的错误收束直接生成记录。
- 保持 `agent_internal` 模式：只有本地准备了内部 payload 时，NK-GeniOS 才调用 `report-to-feishu`。

## 测试与验收


影响文件：

- `Mental-LLM_JxFdj/__tests__/mental-prototype.test.js`
- `Mental-LLM_JxFdj/tests/manual/manual_cases.md`

新增自动化覆盖：

1. “情绪比较压抑”后回答“这几天吧”时，策略仍为 `clarify`，目标为 `functional_impact`，绝不进入收束。
2. 一次单轮短回答不会触发 `summarize`。
3. 只有连续低信息回答或明确结束表达才允许提前进入总结。
4. Agent 收束文案不能单独触发报告；本地 `ready_to_close` 或明确用户结束语才能触发。

新增手工回归：截图所示对话、低信息主动结束、正常完整收束、明确安全情境。完成后运行 `npm run test`、`npm run typecheck` 和项目现有本地验证脚本。

## 风险与边界

- 平台 Agent 的输出不是严格可控程序，因此本地守卫只能降低错误输出的学生可见概率，不能替代平台提供真正的系统级结构化变量能力。
- 隐藏纠偏请求会额外消耗一次 Agent 请求；限制为一次，且不把内部指令或原始错误回复显示给学生。
- 本轮不改变风险分流、身份、飞书字段合同或学生端完整报告可见性。
