## 0. 开发原则

1. 不处理 `initial` 原始项目，只修改 `Mental-LLM_JxFdj`。
2. 保持现有分层：`src/domain` 放领域状态，`src/services` 放业务逻辑，`src/contracts` 放跨端/工作流契约，`src/app` 放页面运行时 glue code。
3. 不把心理测评逻辑写死在 DOM 操作里。
4. 不把学生端展示内容和后台报告内容混在一起。
5. 不宣称临床诊断，不输出诊断结论，只做非诊断、证据化、可复核的支持性评估记录。
6. 保持飞书工作流当前四字段入口：`input`、`SEVERITY_LEVEL`、`Student_ID`、`time`。

## 1. 第一步：建立开发基线

### 目标

确认当前项目可运行、可构建，再开始改设计对齐逻辑。这样后续每次修改都能判断是新改动造成的问题，还是原有问题。

### 操作

1. 进入项目目录：
   ```powershell
   cd D:\Desktop\Software\AIUE\Mental-LLM_JxFdj
   ```
2. 运行类型检查：
   ```powershell
   npm run typecheck
   ```
3. 运行本地 smoke：
   ```powershell
   npm run smoke
   ```
4. 如需完整本地验证：
   ```powershell
   npm run validate:local
   ```

### 验收标准

- `npm run typecheck` 通过。
- `npm run smoke` 输出 `SMOKE_CHECK_PASS`。
- 如果失败，先修复当前基线问题，不进入下一步功能开发。

## 2. 第二步：显式建立 D0-D12 对话阶段模型

### 目标

把设计文档里的 D0-D12 对话流程从“文档描述”落到代码里的可追踪状态。后续每轮对话都要知道当前阶段、已收集信息、缺失信息和下一步动作。

### 新增文件

- `src/domain/dialogueStage.ts`
- `src/services/dialogueStageService.ts`

### 修改文件

- `src/domain/session.ts`
- `src/services/sessionService.ts`
- `src/services/sessionSnapshotService.ts`
- `src/contracts/sessionSnapshotContract.ts`
- `src/app/sessionRuntime.js`
- `src/app/chatRuntime.js`

### 数据结构建议

在 `dialogueStage.ts` 中定义：

- `DialogueStageCode`：`D0_session_init` 到 `D12_report_upload`。
- `DialogueStageState`：当前阶段、已完成阶段、当前轮数、最后更新时间。
- `DialogueTaskStatus`：`pending`、`in_progress`、`done`、`skipped`、`blocked`。
- `DialogueNextAction`：下一步建议动作，例如继续开放式追问、固定安全确认、触发量表、生成报告。

### 开发步骤

1. 在 `src/domain/dialogueStage.ts` 定义 D0-D12 枚举和阶段元数据。
2. 在 `src/services/dialogueStageService.ts` 实现：
   - `createInitialDialogueStageState()`
   - `advanceDialogueStage(state, event)`
   - `getCurrentDialogueStageLabel(state)`
   - `getNextDialogueAction(state, assessmentState, safetyState)`
3. 在 `session.ts` 的 `SessionState` 中加入 `dialogueStage` 字段。
4. 在 `sessionService.ts` 初始化会话时创建 D0 状态。
5. 在 `chatRuntime.js` 每次用户输入后，调用阶段推进逻辑。
6. 在 `sessionSnapshotService.ts` 和 `sessionSnapshotContract.ts` 中输出当前阶段，方便报告和飞书记录追踪。

### 验收标准

- 新会话初始状态为 D0。
- 用户完成边界说明后进入 D1/D2。
- 开放式主诉收集后进入 D3/D4。
- 固定安全确认必须在 D7 被显式记录。
- 报告生成和上传对应 D11/D12。
- session snapshot 中能看到当前 D 阶段。

## 3. 第三步：建立结构化信息收集模型

### 目标

让系统知道一段对话已经收集了哪些心理评估信息，而不是只保存聊天文本。这里是“无感知测评”的核心：从自然对话中逐步整理主诉、情绪、认知、行为、躯体、功能影响、支持资源等字段。

### 新增文件

- `src/domain/assessmentFields.ts`
- `src/services/assessmentStateService.ts`

### 修改文件

- `src/domain/session.ts`
- `src/services/transcriptService.ts`
- `src/services/reportDraftService.ts`
- `src/services/sessionSnapshotService.ts`
- `src/contracts/sessionSnapshotContract.ts`

### 数据结构建议

在 `assessmentFields.ts` 中定义：

- `AssessmentFieldKey`
  - `chief_complaint`
  - `duration`
  - `campus_context`
  - `emotion_state`
  - `cognition_state`
  - `behavior_state`
  - `somatic_state`
  - `functional_impact`
  - `sleep_appetite`
  - `support_history`
  - `risk_disclosure`
  - `scale_result`
- `AssessmentFieldStatus`
  - `not_asked`
  - `asked_no_answer`
  - `partially_collected`
  - `collected`
  - `refused`
  - `conflicting`
- `AssessmentEvidence`
  - 来源 transcript id
  - 用户原话摘要
  - 收集时间
  - 置信度

### 开发步骤

1. 建立 `AssessmentState`，保存字段状态和证据。
2. 在 `assessmentStateService.ts` 实现：
   - `createInitialAssessmentState()`
   - `updateAssessmentField(state, fieldKey, evidence)`
   - `getMissingCoreFields(state)`
   - `summarizeAssessmentProgress(state)`
3. 初期可以采用保守方式：先由对话流程显式标记阶段与字段，不急着做复杂 NLP 自动抽取。
4. 把 `AssessmentState` 接入 session snapshot。
5. 报告生成时引用 `AssessmentState`，明确哪些字段已收集、哪些字段缺失、哪些字段用户拒答。

### 验收标准

- 报告不再只展示最近聊天片段，而是能展示结构化字段。
- 缺失信息能被标记，不把“未询问”误写成“无异常”。
- 用户拒答能被记录为 `refused`，不强行追问。

## 4. 第四步：完善风险识别与处置规则

### 目标

把当前安全摘要升级为“证据化风险判断”。安全通道必须优先于普通对话流程和量表流程。

### 新增文件

- `src/domain/safetyEvidence.ts`
- `src/services/safetyRuleService.ts`

### 修改文件

- `src/domain/safetyStatus.ts`
- `src/app/safetyRuntime.js`
- `src/app/statusNoticeRuntime.js`
- `src/services/reportDraftService.ts`
- `src/services/sessionSnapshotService.ts`
- `tests/manual_cases.md`

### 数据结构建议

在 `safetyEvidence.ts` 中定义：

- `SafetyRuleId`：例如 `RISK_SELF_HARM_IDEATION`、`RISK_PLAN_OR_METHOD`、`RISK_RECENT_ATTEMPT`、`RISK_OTHER_PERSON_QUOTE`、`RISK_NEGATED_DISCLOSURE`。
- `SafetyEvidenceItem`：规则编号、触发文本摘要、来源消息、主体是本人还是他人、是否否定、时间范围、置信度。
- `SafetyWorkflowLabel`：`R0`、`R1`、`R2`、`R3`、`RX`。

### 开发步骤

1. 保留现有 `SafetyStatus` 对外状态，但扩展内部字段，加入 evidence list。
2. 在 `safetyRuleService.ts` 实现规则判断：
   - 识别本人风险表达。
   - 区分“我没有想过伤害自己”这种否定表达。
   - 区分“我朋友说他不想活了”这种他人引用。
   - 区分历史表达与近期表达。
   - 对计划、方法、时间、可及性等高风险要素单独标记。
3. 安全状态变化时，更新 `workflowLabel`。
4. 在 `statusNoticeRuntime.js` 中只展示学生端合适提示，不显示内部规则编号。
5. 报告中写入风险证据摘要和处置建议，但不写诊断。

### 验收标准

- 明确否定风险时，不误报高风险。
- 引用他人风险时，不直接归为学生本人风险。
- 出现明确自伤/自杀计划时，优先进入安全处置，不继续普通测评流程。
- 后台报告能看到风险证据和规则编号。
- 学生端看不到内部风险标签。

### 报告结构建议

   - 会话 ID

   - 是否模拟身份

### 开发步骤

1. 在 `reportTemplate.ts` 定义报告版本、章节类型、字段状态。

4. 保留四字段工作流入口，不改变飞书工具合同。
5. 对报告中的学生原话做必要摘要，不全文倾倒敏感对话。
6. 报告必须显式写“本记录不构成医学诊断”。

### 验收标准

- `REPORT_MARKDOWN` 是中文报告。
- 报告包含信息缺口，不把缺失信息写成确定结论。
- 报告包含风险状态和证据摘要。
- 报告不输出诊断名。
- 飞书 payload 字段名仍然是 `input`、`SEVERITY_LEVEL`、`Student_ID`、`time`。

## 7. 第七步：让学生端交互更贴近“无感知测评”

### 目标

减少问卷感，让学生先自然表达，再由系统渐进式整理评估信息。

### 修改文件

- `index.html`
- `src/app/chatRuntime.js`
- `src/app/messageRuntime.js`
- `src/app/statusNoticeRuntime.js`
- `src/app/formRuntime.js`
- `src/services/chatService.ts`
- `src/utils/sanitizeText.ts`

### 开发步骤

1. 首屏文案强调陪伴式倾听和边界说明，不说“开始心理测评问卷”。
2. 对话开头先开放式主诉，不直接进入 PHQ-9/GAD-7。
3. 根据 D 阶段和缺失字段，生成下一轮追问意图。
4. 固定安全确认放在 D7，表达要自然但清楚。
5. 量表只在必要时触发，触发前说明用途和边界。
6. 学生端永远不显示后台报告全文、飞书 payload、内部风险编号。

### 验收标准

- 一次模拟对话不再像连续填表。
- 学生端展示内容和后台报告内容边界清楚。
- 风险场景下先安全处置，再考虑继续对话。

## 8. 第八步：补充量表触发与计分规则

### 目标

让 PHQ-9、GAD-7 等量表成为“必要时补充”的结构化能力，而不是默认主流程。

### 新增文件

- `src/domain/scaleAssessment.ts`
- `src/services/scaleAssessmentService.ts`

### 修改文件

- `src/app/formRuntime.js`
- `src/app/profileChartRuntime.js`
- `src/services/reportDraftService.ts`
- `tests/manual_cases.md`

### 开发步骤

1. 定义量表类型、题目、选项、分值、总分、解释边界。
2. 实现确定性计分，不依赖模型自由解释。
3. 明确触发条件：
   - 用户主动请求量表。
   - 对话中持续出现焦虑/抑郁相关困扰，需要补充评估。
   - 后台报告缺少必要结构化程度。
4. 报告中写入量表结果，但避免诊断化表述。
5. 若量表未完成，报告写“未完成/未触发/用户拒答”。

### 验收标准

- 同一答卷多次计分结果一致。
- 未完成量表不会生成虚假结论。
- 量表结果只作为补充信息，不覆盖对话证据。
