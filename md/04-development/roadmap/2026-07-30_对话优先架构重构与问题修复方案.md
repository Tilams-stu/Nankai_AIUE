## 1. 文档目的

本方案用于解决真实长对话测试中暴露的系统性问题。重点不是继续修改若干句 Agent 话术，而是重新划分以下职责：

1. 用户当前希望如何交流。
2. 本轮内容在谈论谁、什么主题、执行什么言语行为。
3. 哪些心理评估信息可以从自然表达中旁路提取。
4. 哪些安全、身体、隐私或数据权利请求必须优先处理。
5. 何时允许总结、结束、生成报告和提交工作流。

本方案保留现有页面、`AssessmentState`、本地报告模板和飞书四字段工作流合同，但不再允许测评字段缺口直接控制学生侧 Agent 的下一句话。

## 2. 当前问题结论

### 2.1 核心设计根因

当前主要数据流为：

```text
用户输入
-> assessmentStateService 通过关键词更新字段
-> conversationPolicyService 从缺失字段选 targetField
-> dialogueStageService 将 targetField 映射为 D2-D7 阶段
-> conversationContextService 输出 missingFields/nextQuestionPriority
-> proxy_server.py 要求 Agent 优先围绕 targetField 追问
```

这使系统虽然使用了共情话术，控制逻辑仍然是隐藏问卷。具体表现包括：

- 用户正在展开当前话题时，系统为了补字段主动换题。
- 用户明确要求“不分析”后，该边界只影响单轮文案，没有进入持久状态。
- 最近 Agent 回复没有按顺序进入平台上下文，跨轮承诺无法稳定保留。
- Agent 在缺少追问许可时退化为通用共情模板。
- 安全、隐私、第三方、虚构、身体症状和求助决策问题仍被普通测评策略覆盖。
- 报告提交仍依赖学生侧生成模型是否执行工具调用。

### 2.2 状态职责混合

现有 D0-D12 同时承担以下职责：

- 对话阶段提示。
- 测评字段采集进度。
- 安全确认门控。
- 总结和收尾判断。
- 报告上传阶段记录。

这些状态并不属于同一个状态机。测评进度、互动偏好、安全路由和报告交付必须拆分，否则任一字段变化都会意外改变对话行为。

### 2.3 关键工程矛盾

1. `recentAgentEvidence` 已在浏览器生成，但代理只消费 `recentUserEvidence`。
2. 当前产品明确采用“后台无感测评”：用户不需要点击生成报告，也不提供暂停后台测评的前台控制。
3. 当前运行时会将完整 `AppState` 写入 `sessionStorage`；保存策略不是本轮核心改造，但仍需作为已知限制记录，不能在文案中宣称严格的数据最小化或安全保证。
4. `prepareAgentInternalPayload` 只证明本地 payload 已准备，不证明 Agent 已调用工具或飞书已写入。
5. `SafetyStatus` 只区分本人、第三方和未知，不足以处理虚构、引用、假设和混合主体。

## 3. 重构目标与非目标

### 3.1 目标

1. 对话由用户当前话题和互动边界驱动，字段缺口仅作为后台信息。
2. 测评从自然表达中旁路发生，不为填满字段强制切题。
3. 安全、隐私问答和身体症状由本地确定性规则优先处理；后台测评和报告更新默认自动执行。
4. Agent 只负责受约束的学生可见自然语言，并按照隐藏的本地报告 payload 调用工作流；不决定报告事实。
5. 报告中的每项事实都能追溯到用户原文、修正关系和主体归属。
6. 短会话、拒答安全和提交失败均得到明确终态；用户无需主动触发“生成报告”才能形成后台记录。

### 3.2 非目标

1. 不构建医学诊断系统。
2. 不从自然对话伪造 PHQ-9、GAD-7 或其他量表分数。
3. 不让 Agent 根据语言印象生成未经证据支持的严重程度结论。
4. 不在学生端展示内部风险标签、完整后台报告、系统提示词或工具 payload。
5. 不在本轮重做页面视觉、白噪音、3D 模型或量表页面。
6. 不改变工作流四字段：`input`、`SEVERITY_LEVEL`、`Student_ID`、`time`。

## 4. 目标架构

```text
Student UI
  -> SessionRuntime 记录原始用户轮次
  -> TurnInterpretationService
       - intent / subject / topic / boundary / correction
       - safety signal / medical signal
  -> PriorityRoutingService
       1. immediate safety
        2. privacy question / direct data question
        3. explicit closing
        4. third-party / fictional / quoted content
        5. user question / help-seeking decision
        6. minimal medical caution when clearly necessary
        7. ordinary support conversation
  -> InteractionStateService
  -> ResponsePlanningService
  -> mode-specific ContextPacket
  -> Student-facing Agent
  -> AgentResponseGuardService
  -> visible response

Parallel evidence path:
User turn
  -> AssessmentEvidenceExtractionService
  -> AssessmentState + evidence relation
  -> ReportDraftService

Independent delivery path:
Meaningful self evidence or closing event
  -> ReportAutoUpdateCoordinator
  -> ReportDraftService
  -> hidden Agent workflow payload
  -> report-to-feishu-yhx
  -> created/updated record or unconfirmed/failed audit state
```

### 4.1 架构原则

- UI 只负责显示状态、收集明确操作和调用服务，不编写复杂业务判断。
- `src/domain/` 定义强类型状态和事件。
- `src/services/` 承担解释、路由、决策、提取、报告和交付逻辑。
- `src/app/` 只负责浏览器编排和 DOM 更新。
- Python 代理只负责外部 API、上下文序列化、工具提交和审计，不重新推导业务状态。
- 平台提示词只保留身份边界、语言风格和工具合同；本地状态优先于平台自由判断。

### 6.11 ClosureCoordinatorService

新增：`src/services/closureCoordinatorService.ts`

本地报告自动更新规则：

```text
新的有效本人证据
-> 判断是否已经达到最小可报告条件
-> 若没有记录则 create，已有记录则 update
-> 将最新本地 payload 放入隐藏 Agent 工具上下文
-> 调用 report-to-feishu-yhx
-> 记录 submitted_unconfirmed 或 failed

信息达到最低充分程度
-> 自动再次 update
-> 对话保持 active，允许用户继续补充

用户点击结束按钮或明确结束
-> 进行最后一次强制 update
-> 安全状态 completed/refused/incomplete 均可进入确定收尾
-> 不因 Agent 是否认为对话足够长而跳过报告
```

必须区分：

- `reportDirty`：本轮新增证据导致报告需要 create/update。
- `assessmentSufficient`：信息足够，可以生成更完整的中间报告，但不结束对话。
- `closingRequested`：用户明确希望结束，触发最后一次 update。

三者不能继续合并为同一条件。报告自动更新不要求用户知道，也不要求用户点击“生成报告”。

### 6.12 ReportAutoUpdateCoordinator 的触发和去重

新增：`src/services/reportAutoUpdateCoordinator.ts`

该服务只决定“何时准备或重提 payload”，不决定如何与学生说话。它接收本轮 `AssessmentEvidenceCandidate`、`SafetyStatus`、当前报告 hash 和 `DeliveryState`，输出 `no_change`、`create`、`update` 或 `retry`。

最小可报告条件：

```text
subject=self
AND 本轮至少有一条有效的主要困扰、情绪/睡眠/行为、功能影响、持续时间或安全证据
AND 不是问候、结束语、隐私问题、第三方叙述、虚构文本或纯系统控制语
```

触发规则：

1. 第一次满足最小可报告条件时，准备 create payload。
2. 已有报告后，新增事实、修正事实、睡眠/功能影响补充或安全状态变化时，标记 `reportDirty` 并准备 update payload。
3. 达到 `assessmentSufficient` 时，即使学生继续交流，也准备一次更完整的 update。
4. 用户明确结束、点击结束按钮或安全拒答形成终态时，强制准备最后一次 update。
5. 相同 payload hash 不重复提交；同一时刻只允许一个 `dispatching` 请求。
6. Agent 工具请求未被本地确认时，后续有效变化或最终结束可再次请求；不因一次未确认而永久锁死会话。

这使“至少不会完全没有报告”成为本地可验证的状态要求，同时避免把每句闲聊都当成一次工作流提交。

## 7. Agent 与工作流边界

### 7.1 学生侧 Agent

只负责：

- 根据 `ResponsePlan` 生成自然语言。
- 承接当前话题。
- 在允许时提出一个问题。
- 不生成报告、不决定上传、不声明外部写入成功。

### 7.2 报告提交

当前确定使用 Agent 调用工作流：

```text
Browser -> Local Proxy -> 学生侧 Agent 隐藏工具上下文
        -> report-to-feishu-yhx -> search/create/update Feishu
```

本地不能直接调用工作流。每次自动 update 都由本地生成 payload，再通过 Agent 的隐藏上下文请求工具原样提交。报告工具请求不能要求学生侧 Agent 自己重新总结报告。

DEC-026 所说的“独立工具提交 Agent/请求类型”，不是必须新建一个产品 Agent，而是一个平台能力选项：如果 NK-GeniOS 支持，可以让报告工具调用与学生聊天请求分开；如果不支持，则继续使用同一个 Agent 的隐藏工具请求。

无论哪种方式，都必须：

- 不使用学生侧对话上下文。
- 不产生学生可见回复。
- 仅接受本地四字段 payload。
- 限制调用一次并记录结果。
- 失败后由 `DeliveryState` 控制下一次自动 update 或结束时重试，不依赖自然语言。
- 平台日志只能确认“工具请求是否出现/返回什么”；在本地拿不到最终结果时，状态保持 `submitted_unconfirmed`。

## 9. 关键场景数据流

### 9.1 “先别分析我”或“随便聊聊”

```text
intent=boundary
-> boundary=no_assessment_question, scope=session
-> mode=free_chat
-> assessmentPermission=allowed
-> questionPermission=natural_follow_up
-> Context 不包含 missingFields/targetField
-> 回复具体承接当前内容，可自然开发性追问，但不能问字段
```

### 9.2 隐私问题

```text
intent=privacy_question
-> route=privacy
-> PrivacyFactsService 查找已确认事实
-> 回答数据用途、访问、留存和控制
-> 本轮禁止心理字段追问
```

### 9.3 第三方或小说内容

```text
subject=third_party/fictional/quoted
-> 不更新本人安全状态和 AssessmentState
-> 第三方：回答如何支持对方
-> 虚构：完成安全范围内的创作请求
-> 只有出现额外本人线索时才澄清本人状态
```

### 9.4 短会话结束并拒答安全

```text
closingRequested=true
-> safety=refused/incomplete
-> 自动生成信息有限报告并通过 Agent update
-> 不再依赖 Agent 判断会话是否足够长
```

### 9.5 信息充分但用户继续交流

```text
reportableEvidenceChanged=true
-> ReportAutoUpdateCoordinator 生成当前本地报告
-> 通过 Agent 隐藏工具上下文执行 update
-> 对话仍保持 active
-> 用户新增事实后再次 update
```

### 9.6 身体不适

```text
medicalSignal=true
-> 输出最低限度的非诊断性现实就医提醒
-> 不直接归因为心理问题
-> 本轮不切换成完整医疗问诊流程
```

## 10. 技术选型

| 范围 | 选型 | 理由 |
| --- | --- | --- |
| 状态与规则 | TypeScript 领域接口 + 纯 Service | 可测试、与 DOM 解耦、延续现有项目结构 |
| 明确高权限路由 | 本地确定性规则 | 不允许模型编造安全、隐私和提交决定 |
| 普通语义解释 | 规则优先，可选结构化 LLM 抽取 | 提高自然语言覆盖，同时保留 Schema 校验 |
| 对话生成 | 现有 NK-GeniOS Agent | 保留当前接入和自然语言能力 |
| 报告事实 | 本地证据状态与模板 | 继续保持本地唯一真相源 |
| 工作流 | 现有四字段工作流 | 不改变已验证的飞书合同 |
| 测试 | Node `node:test` + 现有 PowerShell 集成脚本 | 沿用当前测试工具链 |

## 13. TDD 与验证要求

按照 clean architecture 工作流，开发阶段先补测试并确认失败，再实现服务和 UI 编排。

### 13.1 单元测试

至少覆盖：

1. “先别分析/随便聊聊”形成持久边界，后续轮次不恢复字段驱动追问，但仍允许自然交流。
2. `recentDialogueTurns` 保持用户/Agent 时间顺序。
3. 并列话题不直接选择 duration/functional impact。
4. 隐私问题不更新 AssessmentState、不追加字段问题。
5. 第三方、虚构和引用风险词不更新本人风险状态。
6. 明确本人风险仍进入正确安全路径。
7. “想躲起来但不是伤害自己”不会被定义成明确自伤意图。
8. 明显身体症状不会被直接归因为心理问题或触发字段追问。
9. 问候和结束语不进入主诉。
10. 睡眠和学习/社交影响按分句写入不同字段。
11. 修正事实会 supersede 旧证据而不是简单拼接。
12. `questionPermission=forbidden` 时追问触发守卫。
13. `allowClosure=false` 时主动结束触发守卫。
14. 安全拒答后仍能得到确定收尾结果。
15. 首个有效本人困扰创建报告，后续有效证据自动 update，同一 payload 不重复触发。
16. prepared、dispatching、submitted_unconfirmed、failed 状态不会混淆。

### 13.2 集成测试

1. 浏览器 -> Context V2 -> 代理的有序对话传输。
2. 学生侧 Agent 与工具提交请求的上下文隔离。
3. 首次自动创建、对话中自动 update、明确结束和拒答安全四条报告分支。
4. 工作流首次创建和同会话更新。
5. 代理重启后健康接口显示当前工作流名称和版本。
6. 报告中主诉、睡眠、功能影响和安全措辞与本地证据一致。

### 13.3 验收原则

- 不以“Agent 大多数时候表现正常”作为通过标准。
- 高权限分支必须由状态和测试断言证明。
- Agent 不合规时必须有一次重写或本地回退。
- 外部工作流未确认时不得向学生显示“已成功写入”。
- 未确认字段允许留白，不以字段完整率作为对话成功标准。

## 15. 方案确认边界

以下技术原则已经可以由现有证据直接确定，无需再次讨论：

- 最近对话必须按顺序包含用户和 Agent。
- 测评字段缺口不得直接控制普通对话。
- 第三方和虚构内容不得写入本人报告。
- 身体安全、本人即时风险、隐私和明确结束高于普通测评。
- 工作流四字段继续保持不变。
- 报告事实继续以本地证据状态为唯一来源。
- UI 不承载复杂业务逻辑。
- 后台报告在首次有效本人困扰后自动创建，并在有效证据变化时自动 update。
- “先别分析/随便聊聊”禁止字段驱动追问，但不暂停后台测评提取。
- 本地必须通过 Agent 调用 `report-to-feishu-yhx`，不能直接调用工作流。

仍需产品、数据或平台决策的事项见：

`roadmap/2026-07-30_对话重构待确认决策清单.md`

已确认的产品规则直接按本方案实现；仍未确认的权限、留存、现实资源和平台回执能力，仅以保守文案和 `submitted_unconfirmed` 状态处理，不能自行编造外部承诺。
