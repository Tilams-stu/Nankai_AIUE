# 对话策略与会话闭环下一步改造方案

日期：2026-07-29  
适用项目：`D:\Desktop\Software\AIUE\Mental-LLM_JxFdj`

## 1. 目标

本次改造解决上一阶段之后仍然存在的产品问题：

1. 智能体像问卷一样连续追问，无法自然聊天。
2. 用户已经表达过的信息被换一种说法重复确认。
3. 未提到“报告”或未点击按钮时，会话不会自然收束。
4. 结束时安全问题突然出现，并且可能重复出现。
5. 自然语言没有命中关键词时，本地状态仍显示“未询问”。
6. Agent 内部调用飞书时，必须使用本地生成的完整 payload，不能重新编写报告。
7. 页面刷新或代理重启后，会话连续性和 Agent conversation 映射可能丢失。

改造后的产品定位：

> 前台是帮助用户表达、梳理和获得下一步建议的对话；后台在不打断对话的情况下完成必要的信息整理和安全筛查。未知字段允许存在，不为了填满字段而追问。

## 2. 当前审查结论

### 2.1 已经具备的能力

- 本地 `AppState` 已保存 transcript、assessment、safety、dialogue stage 和 upload 状态。
- 每轮聊天已经可以向服务端发送 `local_context_packet`。
- 报告已经由本地 `reportDraftRuntime` 和模板生成，工作流四字段合同仍保持 `input`、`SEVERITY_LEVEL`、`Student_ID`、`time`。
- 本地 typecheck 和现有 6 个单元测试通过。

### 2.2 必须优先修复的问题

1. `server/proxy_server.py` 的上下文指令仍要求“优先补齐未确认字段”，会把可选字段变成强制问卷。
2. `conversationContextService.ts` 把所有未收集字段放入下一步优先级，没有“最低充分信息”和“继续追问收益很低”的概念。
3. `assessmentStateService.ts` 在收到不同描述时直接标记 `conflicting`，兼容的多段证据也会重新变成缺口。
4. 字段抽取主要依赖关键词，无法稳定识别“还好、白天没精神、没受影响、就是最近不太想说”等自然回答。
5. `dialogueStageService.ts` 仍按字段是否 `not_asked` 线性推进，阶段状态与真实对话意图没有完全对齐。
6. `pageRuntime.js` 只在点击结束时硬插入安全问题，且只显示消息，没有记录安全问题已发出。
7. `safetyRuleService.ts` 对 D7 中没有命中风险关键词的回答存在过宽的默认完成行为；简单回答“没有”也可能没有形成完整的 `risk_disclosure` 证据。
8. `uploadRuntime.js` 主要依赖“报告、总结、先到这里”等固定词识别结束，不支持“信息已经足够”的内部收束事件。
9. `agent_internal` 模式目前只能在本地生成审计确认；真实 Agent 工具调用是否收到本地完整 payload，仍没有端到端证据。
10. 会话状态和代理的 `conversation` 映射都主要存在内存中，刷新页面、代理重启或映射丢失后可能断裂。

## 3. 总体架构

保留现有“本地状态 -> 本地报告 -> 工作流”的主链路，在中间增加一个确定性的对话决策层：

```text
用户输入
  -> 本地安全监测
  -> 本地字段抽取/证据合并
  -> 对话策略决策器
       -> respond：承接，不提问
       -> clarify：只问一个高价值问题
       -> safety_check：一次常规安全确认
       -> summarize：自然总结并允许更正
       -> close：生成本地报告并进入上传
       -> safety_route：危机流程
  -> 将策略和本地状态注入 Agent
  -> Agent 只负责自然语言表达
  -> 本地 payload 负责报告来源
  -> Agent 内部工具或 forward gateway 负责工作流调用
```

模型负责语言理解和表达；本地代码负责字段状态、停止条件、安全门控、报告 payload 和上传来源。不能让模型自行决定报告内容或通过“记忆”决定是否完成评估。

## 4. 分阶段实施步骤

### P0-1：修复状态合并和安全回答

目标：先消除“已回答但重新变成缺口”的确定性错误。

影响文件：

- `src/services/assessmentStateService.ts`
- `src/domain/assessmentFields.ts`
- `src/services/safetyRuleService.ts`
- `src/domain/safetyStatus.ts`
- `src/app/sessionRuntime.js`
- `__tests__/mental-prototype.test.js`

步骤：

1. 将“不同描述”和“真正冲突”分开。不同描述默认追加 evidence 并保持 `partially_collected` 或 `collected`；只有明确互相否定的内容才使用 `conflicting`。
2. 为字段保留 `lastAskedField`、`lastAskedTurn` 和证据列表，后续用于重复问题拦截。
3. 在安全筛查上下文中识别“没有、没有过、目前没有、否”等明确否认，并将用户原话写入 safety evidence 和 `risk_disclosure`。
4. 将安全状态扩展为至少 `not_started`、`prompted`、`completed`、`refused`、`incomplete`，区分“没问”“已问未答”和“用户拒答”。
5. 安全问题的显示必须通过 session runtime 记录为 agent transcript，不能只调用 `appendMsg`。

验收：

- 用户连续描述两种情绪表现后，字段不变成冲突缺口。
- 用户回答“没有”后，安全筛查只需一次，不会因字段仍是 `not_asked` 再次阻塞。
- 用户说“不方便回答”后，记录为拒答/信息不足，不被解释成安全否认。

### P0-2：建立“最低充分信息”和对话策略决策器

目标：让未完成所有字段的会话也能合理结束。

新增文件：

- `src/domain/conversationPolicy.ts`
- `src/services/conversationPolicyService.ts`

影响文件：

- `src/domain/dialogueStage.ts`
- `src/services/dialogueStageService.ts`
- `src/services/conversationContextService.ts`
- `src/contracts/chatContract.ts`
- `src/app/chatRuntime.js`

建议的数据结构：

```ts
type ConversationResponseMode =
  | "respond"
  | "clarify"
  | "safety_check"
  | "summarize"
  | "close"
  | "safety_route";

interface ConversationPolicy {
  responseMode: ConversationResponseMode;
  completionStatus: "gathering" | "sufficient" | "awaiting_safety" | "ready_to_close" | "completed";
  targetField?: AssessmentFieldKey;
  reason: string;
  repeatedTopic?: string;
  lowInformationTurns: number;
}
```

最低充分信息建议定义为：

1. 主诉或求助目标已获得。
2. 持续时间或近期变化至少有一个。
3. 情绪、行为、身体、睡眠中至少有一个表现，或用户明确表示没有明显变化。
4. 至少有一个功能影响判断，或用户明确表示没有明显影响。
5. 安全状态已完成、明确拒答，或被标记为信息不足。

步骤：

1. 新增 `hasMinimumSufficientInfo(state)`，不要用“所有字段都不是 `not_asked`”作为完成条件。
2. 将校园情境、认知、身体、睡眠、支持系统、量表定义为按需字段，只有与主诉或风险判断直接相关时才加入追问候选。
3. 新增 `responseMode` 到 `local_context_packet`，让 Agent 知道本轮可以只回应、不必提问。
4. 只有当问题能改变主诉理解、风险分流或下一步建议时，才返回 `clarify`。
5. 同一主题在最近 2-3 轮已经问过时，强制禁止再次追问，除非本轮出现明确矛盾。
6. 连续两轮没有新信息、用户连续简短回答或最低信息已满足时，切换到 `summarize`。
7. `dialogueStageService` 保留 D0-D12 阶段用于审计，但阶段推进不再把所有 `not_asked` 字段当成阻塞条件。

验收：

- 模拟“最近一个月烦、睡眠正常、学习没有明显影响”的对话，不再连续询问情绪的近义问题。
- 最低信息满足后，即使支持系统、量表等字段为空，也能进入总结。
- Agent 收到 `responseMode=respond` 时可以只承接，不被上下文要求继续提问。

### P0-3：升级字段抽取，保留本地状态为唯一真相源

目标：减少“自然表达没有命中关键词”的误判。

第一阶段影响文件：

- `src/services/assessmentStateService.ts`
- `src/services/safetyRuleService.ts`
- `__tests__/mental-prototype.test.js`

第二阶段可新增：

- `src/contracts/turnExtractionContract.ts`
- `src/services/turnExtractionService.ts`

步骤：

1. 先补充常见自然表达、否定表达、程度表达、功能影响表达的单元测试。
2. 把“关键词命中”定义为低置信度证据，而不是直接当作完整字段。
3. 如果平台支持结构化输出，让 Agent 每轮返回 `state_update`；如果不支持，增加一个隐藏的结构化抽取调用，学生端只展示 `user_message`。
4. 抽取结果只写入本地 `AssessmentState`，Agent 的自然语言不能直接覆盖状态。
5. 报告中将缺口改为“本次对话未涉及/用户未回答/信息存在冲突”，不要全部显示为“未询问”。

验收：

- “白天主要在机房待着”“还行”“没有明显影响”“最近不太想说”等表达有可追溯状态。
- Agent 回复内容变化不会改变本地报告字段。
- 所有字段都有 evidence、来源和状态。

### P0-5：实现自然收束和本地 payload 传递

影响文件：

- `src/app/chatRuntime.js`

- `src/services/workflowPayloadService.ts`

步骤：

1. 将结束条件从固定关键词扩展为本地 `ConversationPolicy` 事件。
2. `summarize` 阶段输出短总结；用户确认、更正或不再补充时产生 `close` 事件。
3. 用户不提“报告”也可以进入后台生成，但学生端只显示结束反馈，不显示完整报告。
4. 普通 `local_audit`、`mock_success`、`forward` 路径继续由本地 payload 提交。
5. `agent_internal` 路径必须把本地生成的四字段 payload 一并注入 Agent 的隐藏工具上下文，字段至少为：

```json
{
  "input": "本地生成的 REPORT_MARKDOWN",
  "SEVERITY_LEVEL": "本地安全状态映射值",
  "Student_ID": "本地会话身份中的学号",
  "time": "本地生成时间"
}
```

6. Agent 内部路径的工具指令必须明确：只调用 `report-to-feishu`，使用收到的 payload 原样提交，不重新生成、重写或补充报告。
7. 本地代理的 `agent_internal` 审计记录必须保存 payload 摘要、payload hash、会话 ID 和工具调用结果，不能把本地 acknowledgement 当成真实 Feishu 成功。
8. Agent 内部调用和 Feishu 行可见性必须增加一次真实环境人工验收。

验收：

- 用户只说“那今天先这样”或在总结后表示“好的”，可以完成后台记录。
- Agent 内部调用时，飞书收到的 `input` 与本地报告 payload 内容一致。
- Agent 不能通过自己的自然语言记忆重新写出另一份报告。
- 本地显示明确区分“已生成本地 payload”“已请求 Agent 工具”“已确认 Feishu 写入”。

## 5. 不可改变的边界

1. 不把 Agent 作为最终报告来源。
2. 不允许模型自行判断“无风险”或生成诊断。
3. 不在学生端展示完整后台报告、风险内部标签、隐藏上下文或 payload。
4. 不改变工作流四字段名称：`input`、`SEVERITY_LEVEL`、`Student_ID`、`time`。
5. 浏览器不直接持有飞书密钥，不绕过代理和既有工作流权限。
6. 安全监测必须持续存在；自然化不等于取消安全确认。
7. 对高风险、拒答安全或安全信息不足的会话，必须保留人工复核/现实支持分流状态。
8. 不进行与本次目标无关的 UI 重写、模型替换或大范围目录迁移。

## 6. 测试与验收顺序

### 单元测试

1. 兼容的多段字段证据不标记冲突。
2. 明确互相否定的字段才标记冲突。
3. D7 回答“没有”完成安全确认。
4. D7 回答“不方便回答”记录为拒答/信息不足。
5. 最低信息满足时策略返回 `summarize`。
6. 可选字段缺失时策略不返回 `clarify`。
7. 最近重复主题会被拦截。
8. `agent_internal` payload 与本地报告 payload 相同。

### 集成测试

1. 复现截图中的连续对话，验证同一主题最多一次有效追问。
2. 不说“报告”也能自然总结并生成本地 payload。
3. 点击结束前未安全确认时，只出现一次有过渡的安全问题。
4. 页面刷新后恢复会话，或明确提示恢复失败。
5. `mock_success`、`local_audit`、`forward`、`agent_internal` 四种路径都能验证 payload 来源。

### 真实环境测试

1. 使用真实 NK-GeniOS Agent 进行完整对话。
2. 在 Agent 日志或工具输入中确认收到的就是本地 payload。
3. 确认 Agent 调用 `report-to-feishu` 后，飞书多维表格出现对应记录。
4. 用 payload hash 对比本地审计记录和工具输入，证明没有被 Agent 重写。

## 7. 推荐交给低成本模型的执行方式

不要把整个方案一次性丢给模型。按下面顺序逐个任务执行，每完成一个任务都运行测试：

1. 只做 P0-1：状态合并和安全回答。
2. 只做 P0-2：对话策略和最低充分信息。
3. 只做 P0-3：字段抽取和信息缺口表达。
4. 只做 P0-4：上下文包和 Agent 提示词。
5. 只做 P0-5：自然收束和 Agent 内部 payload。
6. 最后做 P1：会话持久化与调试信息。

每次执行的固定要求：

- 先阅读本任务涉及的现有文件，再修改。
- 只修改任务列出的文件，不顺手重构其他模块。
- 不删除现有测试和工作流兼容路径。
- 完成后运行 `npm run typecheck`、`npm run test`，涉及脚本时再运行 `npm run smoke` 和 `npm run validate:local`。
- 在最终报告中说明哪些是真实外部验证，哪些只是本地 mock/audit 验证。
