## 1. 方案目标

当前平台链路已经基本跑通：本地会话状态在记录，Genios 对话在响应，工作流/飞书链路也已经具备可用路径。现在要解决的不是“能不能上传”，而是“上传的报告和后续追问到底以谁为准”。

本次改造目标是把系统从三条并行链路收敛为一条可控业务链路：

1. 本地 `session + assessment + transcript + safety + upload` 是正式信息沉淀和报告生成的唯一真相源。
2. Genios 继续负责自然语言对话，但每轮必须能看到本地结构化状态摘要。
3. 收尾不再依赖“让模型自己回忆并生成报告”，而是使用本地确定性报告 payload。
4. 工作流/飞书写入继续保留当前边界，不让浏览器直连飞书，不向学生端展示完整后台报告。

### 2.2 已确认的断点

当前 `src/app/chatRuntime.js` 发送给 Genios 的请求主体仍然主要是当前用户输入：

```js

```

```python
query = self.extract_query(body)
```

这意味着即使浏览器本地已经更新了 assessment fields、safety、dialogue stage，Genios 每轮并不能稳定看到这些状态。

当前 `src/app/pageRuntime.js` 在 `agent_internal` 模式下的收尾仍然发送隐藏自然语言指令：

```js
const finalizeInstruction =

```

这会继续让最终报告依赖 Genios 自己的会话记忆，而不是依赖本地确定性 payload。

## 3. 技术选型

### 3.1 真相源选择

正式报告真相源选择：本地结构化状态。

理由：

1. 本地状态可追踪、可测试、可导出 snapshot。
2. 本地报告模板已经能把缺失字段、安全状态、上传状态写成稳定 markdown。
3. Genios 的自然语言上下文受会话连续性、代理内存和模型表现影响，不适合作为唯一正式报告来源。

### 3.2 对话上下文同步方式

采用“本地结构化状态摘要 -> 隐藏上下文包 -> 合成 Query”的方式。

原因：当前服务端上游接口只发送一个 `Query`，不能直接传 OpenAI 风格的多条 system/user message。最小可行改法是让前端或服务端把本地状态摘要与用户本轮输入合成为一个模型可读但学生端不可见的文本包。

### 3.3 报告上传方式

P0 默认路径：`finalizeSession()` 调用 `MentalUploadRuntime.finalizeCurrentSession()`，由本地 `reportDraftRuntime` 生成 payload，再提交到 `/api/workflow/report-to-feishu`。

对 `agent_internal` 的处理：

1. 本地仍先生成正式 `REPORT_MARKDOWN`。
2. 若真实 Feishu 必须由 Genios Agent 内部工具完成，则隐藏指令必须携带本地生成的报告 payload，要求 Agent 只转交 payload 调用 `report-to-feishu`，不得重新生成报告。
3. 如果当前本地 `agent_internal` gateway 已能写审计并返回确认，则优先使用 gateway 确认本地 payload 已进入后台提交边界，把“真实 Feishu 可见性”留给人工外部确认。

## 5. 新数据流设计

### 5.1 每轮对话数据流

```text
用户输入
  -> MentalSessionRuntime.ingestUserTurn()
  -> transcript / assessment / safety / dialogueStage 更新
  -> ConversationContextService.buildContextPacket(currentState)
  -> ChatRuntime 将 context packet 与本轮用户输入提交给 /api/chat
  -> Proxy 合成单个 Query 发给 Genios
  -> Genios 基于“已确认字段 / 缺失字段 / 下一步优先项”生成自然追问
  -> agent 回复写回 transcript
```

### 5.2 收尾报告数据流

```text
点击 结束并生成记录
  -> finalizeSession()
  -> 校验本地必填项和安全确认
  -> MentalReportDraftRuntime.buildCurrentReportPayload()
  -> WorkflowPayloadService.validatePayload()
  -> MentalUploadRuntime.submitReportViaGateway()
  -> /api/workflow/report-to-feishu
  -> agent_internal / local_audit / forward / mock_* 对应处理
  -> upload state 更新为 processing / submitted_pending_confirmation / failed_needs_investigation
```

### 5.3 agent_internal 特殊数据流

如果必须由 Genios Agent 内部调用 `report-to-feishu`，则不能再让 Agent 自行生成报告。应改为：

```text
本地生成 REPORT_MARKDOWN + SEVERITY_LEVEL + STUDENT_ID + TIME
  -> 发送隐藏工具调用指令给 Agent
  -> 指令中明确“只能使用以下 payload 调用 report-to-feishu，不得重写报告”
  -> Agent 调用工作流
  -> 本地状态只标记 submitted_pending_confirmation
  -> 飞书行可见性由人工或后续回调确认
```

### 阶段 1：新增本地上下文摘要服务

目标：把当前本地状态转换成短、稳定、模型可读的隐藏上下文包。

新增：

- `src/domain/conversationContext.ts`
- `src/services/conversationContextService.ts`

建议上下文包字段：

```ts
interface ConversationContextPacket {
  schemaVersion: "conversation_context_v1";
  sessionId: string;
  currentStage: string;
  confirmedFields: Array<{ key: string; label: string; value: string; status: string }>;
  missingFields: Array<{ key: string; label: string; status: string }>;
  safety: {
    screeningStatus: string;
    summary: string;
    nextRequiredAction: string;
  };
  nextQuestionPriority: string[];
  avoidRepeatingFields: string[];
  recentUserEvidence: string[];
}
```

实现要求：

1. 不把完整 transcript 全量塞给模型，只放最近 3-5 条摘要和字段证据。
2. 缺失信息必须明确为 `not_asked`、`asked_no_answer`、`refused` 等状态。
3. 安全字段只给模型必要行动信息，不让学生端显示内部风险标签。
4. 控制上下文长度，避免每轮 Query 被大量模板淹没。

验收：构造一个已有字段的测试 state，能输出包含“已确认字段、缺失字段、下一步优先项”的摘要。

### 阶段 2：改造聊天请求，把本地上下文同步给 Genios

目标：每轮让 Genios 稳定看到本地已沉淀状态，减少重复追问。

修改：

- `src/app/chatRuntime.js`
- `src/contracts/chatContract.ts`
- `server/proxy_server.py`

前端改法：

1. `sendConversation()` 在 `recordUserTranscript` 完成后读取最新 `MentalSessionRuntime.getState()`。
2. 调用 `ConversationContextService.buildContextPacket(state)`。
3. 在请求 body 中新增可选字段 `local_context_packet`，或在 `additional_messages` 中加入一条 hidden/system-like message。
4. hidden/silent 用户输入仍写入 transcript，但不展示到学生端。

服务端改法：

1. `extract_query(body)` 不再只取最后一条 `additional_messages`。
2. 如果存在 `local_context_packet`，合成如下 Query：

```text
[本地结构化会话状态]
...context packet...

[对话要求]
请基于已确认字段继续追问，避免重复询问已确认字段。缺失字段优先按 nextQuestionPriority 推进。不要生成后台报告，除非收到明确收尾 payload 指令。

[用户本轮输入]
...user text...
```

3. 上游仍只收到一个 `Query`，不改变 NK-GeniOS 当前代理调用方式。

验收：同一会话中用户已经回答“睡眠差、持续一个月”后，下一轮发送给服务端的 query 包含这些已确认字段，模型不应继续机械追问同一字段。

### 阶段 3：收尾前增加本地完整性校验

目标：点击“结束并生成记录”时，先用本地规则判断是否允许生成正式报告。

修改：

- `src/app/pageRuntime.js`
- `src/services/assessmentStateService.ts`
- `src/services/reportDraftService.ts`

最小校验规则建议：

1. `risk_disclosure` 不能是 `not_asked`。
2. `safety.screeningStatus` 必须是 `completed`，或明确进入 `RX/R1/R2/R3` 等需人工跟进状态。
3. `chief_complaint` 至少 `partially_collected` 或 `refused`。
4. `duration`、`functional_impact`、`support_history` 可以缺失，但必须在报告“信息缺口”中显式列出。
5. 用户拒答不能阻塞报告，但必须写成 `refused`，不能写成“无”。

如未满足安全确认：继续沿用现有安全追问拦截。

如只缺普通字段：允许生成“信息不足版报告”，但上传状态应标记为待人工复核。

验收：安全未确认时不能生成正式记录；普通字段缺失时报告中出现信息缺口，而不是空白或“未询问”大面积散落。

### 阶段 4：改造 `agent_internal` 收尾路径

目标：取消默认隐藏自然语言“让智能体自己生成报告”。

修改：

- `src/app/pageRuntime.js`
- `src/app/uploadRuntime.js`
- `server/proxy_server.py`
- `docs/operations/direct_use_app_guide.md`

推荐 P0 实现：

1. `finalizeSession()` 不再在 `agent_internal` 下优先调用 `sendMessage(finalizeInstruction)`。
2. 所有模式先调用 `MentalUploadRuntime.finalizeCurrentSession()`。
3. `agent_internal` 模式下，由 `/api/workflow/report-to-feishu` 写本地审计并返回 `submitted_pending_confirmation`。
4. 学生端只显示“记录已提交待后台确认”。
5. 文档明确：真实 Feishu 行可见性仍需人工确认或后续 callback 机制。

如果必须保留 Agent 内部工具调用：

1. 新增 `MentalUploadRuntime.submitPayloadViaAgentInstruction(payload)`。
2. 隐藏指令中包含完整四字段 payload。
3. 指令必须写明“不得重新生成报告，不得改写字段，只调用 report-to-feishu”。
4. 该路径只作为 `agent_internal_tool_call` 子模式，不能作为默认报告生成源。

验收：点击收尾后，本地 audit record 中的 `request.input` 与本地 `REPORT_MARKDOWN` 一致；不会再出现 Genios 自称“之前没有具体聊过”的报告。

### 阶段 5：增加 payload 校验和审计摘要

目标：阻止空报告、错字段、错误来源进入工作流。

修改：

- `src/services/workflowPayloadService.ts`
- `src/contracts/workflowContract.ts`
- `src/services/workflowService.ts`
- `server/proxy_server.py`

校验规则：

1. `REPORT_MARKDOWN` 长度必须大于最小阈值，例如 500 字符。
2. `REPORT_MARKDOWN` 必须包含报告版本、信息缺口、安全摘要、使用范围与局限。
3. `SEVERITY_LEVEL` 必须属于非诊断枚举。
4. `STUDENT_ID` 不能为空。
5. `TIME` 必须存在。
6. 工作流四字段映射仍保持 `input`、`SEVERITY_LEVEL`、`Student_ID`、`time`。

审计摘要建议增加：

- `reportVersion`
- `sourceOfTruth: "local_structured_state"`
- `missingFieldCount`
- `confirmedFieldCount`
- `finalizeMode`

验收：构造空报告或缺字段 payload 时，本地直接失败并显示非技术化状态，不进入工作流。

## 7. 优先级排序

| 优先级 | 任务 | 原因 |
| --- | --- | --- |
| P0 | 本地上下文摘要服务 | 解决每轮对话不知道已收集信息的问题 |
| P0 | 聊天请求注入本地状态 | 直接减少重复追问和单机问答感 |
| P0 | 收尾改为本地 payload | 解决报告与真实对话脱节的核心问题 |
| P0 | payload 校验 | 防止错误报告进入飞书链路 |
| P0 | 确定性收尾测试 | 避免后续回归到模型自由生成报告 |
| P1 | agent_internal_tool_call 子模式 | 适配必须由 Agent 内部调工具的真实部署限制 |
| P1 | 调试面板显示结构化状态摘要 | 便于测试人员判断系统是否真的“吃进去”信息 |
| P1 | 会话 snapshot 恢复增强 | 降低代理重启或会话映射丢失导致的断裂感 |
| P2 | 文档和汇报口径更新 | 保证交接和汇报不再混淆“链路打通”和“报告可信” |

## 8. 风险与边界

1. 上下文包过长会稀释用户输入，需要控制摘要长度。
2. 本地关键词抽取仍然比较保守，不能把它包装成临床判断。
3. `agent_internal` 的真实 Feishu 写入如果没有回调，本地最多只能标记“提交待确认”，不能标记“飞书已成功”。
4. 如果 Genios Agent 必须保留报告生成能力，也只能作为辅助表达，正式上传内容仍以本地 payload 为准。
5. 当前设计不改变浏览器不得直连 Feishu、不得持久化学生敏感信息、学生端不得展示完整后台报告的边界。

## 9. 最小可交付版本

最小可交付版本只做 P0：

1. 新增 `ConversationContextService`。
2. 每轮 `/api/chat` 请求携带本地状态摘要。
3. `finalizeSession()` 统一走本地 `finalizeCurrentSession()`。
4. `agent_internal` 不再让模型自由生成报告。
5. 增加 payload 校验和确定性收尾测试。

完成后应能证明：

1. 前面说过的信息会进入后续追问上下文。
2. 最终报告来自本地结构化状态和报告模板。
3. 工作流写入内容可审计、可复核。
4. 学生端只看到简短状态，不看到后台报告全文。

```text
- 工作流四字段入口保持 input、SEVERITY_LEVEL、Student_ID、time 不变。
- 学生端不得展示完整后台报告、内部风险编号、飞书 payload。
- 每完成一个阶段运行 npm run typecheck、npm run test、npm run smoke。
```

## 11. Roadmap 结论

本次改造的主线不是重写平台，而是把已有能力接成一条单一、可控、可验证的业务链路：

```text
本地状态沉淀 -> 本地状态摘要同步给 Genios -> 本地确定性报告生成 -> 工作流上传 -> 审计与人工确认
```

只要 P0 完成，当前“回答没有真正沉淀”和“报告与对话脱节”的核心问题就能被工程化压住。P1 再处理真实 agent_internal 工具调用、调试面板和会话恢复，P2 再补文档和汇报口径。
