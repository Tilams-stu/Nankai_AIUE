
## 5. 研究成果主线

已有访谈材料经过本轮整理后形成：

```text
11 份访谈材料 → 183 条编码记录 → 20 项智能体设计需求
```

PPT 中应准确表述为：

> 基于已有访谈材料完成系统化编码和需求提炼，形成 183 条编码记录和 20 项智能体设计需求。

不要表述为“本轮完成了 11 次访谈”，除非用户另行确认亲自参与了访谈获取过程。

研究发现重点包括：

1. 无感知测评不能简单变成连续的问卷式追问。
2. 系统需要允许学生先自然表达，再围绕当前话题补充结构化信息。
3. 风险识别需要贯穿整个对话过程，而不是只在最后判断一次。
4. 后台报告需要区分原始表达、结构化字段、风险依据和信息缺口。
5. 学生端和后台之间需要明确的数据与展示边界。
6. 系统必须保持非诊断定位，并在高风险场景下提供现实支持资源提示。

### 第 3 页：访谈材料如何变成可实现需求

展示研究路径：

```text
已有访谈材料 → 编码分析 → 主题归纳 → 需求提炼
             11       183          20
```

这一页的重点不是数字本身，而是说明研究分析如何进入系统设计。

### 第 4 页：研究发现改变了系统设计

用四组“研究发现 → 设计回应”：

- 不能一上来连续追问 → 对话优先，后台提取字段；
- 风险会在多轮对话中出现 → 全程监测与证据记录；
- 学生表达可能模糊、拒答或更正 → 支持跳过、修正、结束和信息缺口；
- 后台结果需要可复核 → 原始证据、结构化字段和报告状态分离。

### 第 5 页：最终智能体的设计原则

六项原则：

1. 主诉驱动，字段补全；
2. 风险监测全程在线；
3. 有限共情，不假装治疗关系；
4. 证据与结论分离；
5. 最小必要采集；
6. 后台静默报告与资源提示。

补充边界：系统不是心理医生、心理咨询师或诊断系统；报告是非诊断性的后台记录和项目分析依据。

### 第 6 页：最终系统总体架构

展示：

```text
学生端
  ↓
会话与本地状态
  ├─ transcript
  ├─ dialogue stage
  ├─ assessment state
  └─ safety evidence
  ↓
本地代理 / NK-GeniOS Agent
  ↓
Agent 内部 report-to-feishu-yhx 工作流
  ↓
飞书留档
```

报告草稿与工作流 payload 由本地状态生成并随 Agent 请求传递；本地 gateway/audit 负责本地校验、审计和错误处理，不把浏览器设计成直接连接飞书。重点是解释浏览器层、状态层、Agent 层和外部留档层的职责分离。

### 第 7 页：核心闭环如何工作

主流程：

```text
学生自由表达困扰
→ 系统回应当前话题
→ 后台沉淀主诉和相关信息
→ 自动创建或更新非诊断报告
→ 对话仍可继续
```

这一页是整套 PPT 的核心。要突出学生不需要填写完整问卷，也不需要点击“生成报告”。

## 8. 最终录屏和飞书证据要求

最终录屏建议使用合成学号和合成对话，不使用真实学生数据。

录屏场景：

1. 学生自然表达一项主诉；
2. 补充持续时间、情绪或功能影响；
3. 系统后台出现第一条报告记录；
4. 学生继续询问建议；
5. 学生更正一条信息；
6. 飞书原记录更新，且没有产生重复记录。

外部证据链：

```text
本地 audit 记录
→ Agent 内部工作流调用
→ 工作流执行记录
→ 飞书创建记录
→ 同一 sessionId 对应记录更新
```

飞书截图需要隐藏真实姓名、真实学号、其他学生记录、API Key、Token 和无关工作区信息。

## 14. 研究到实现的追溯矩阵

PPT 的每一个重要设计判断都应能回答“来自哪类研究证据、变成了什么需求、最后落到什么实现”。

| 研究证据/问题 | 设计结论 | 需求或规则 | 实现与展示证据 |
| --- | --- | --- | --- |
| 用户不愿被问卷化，表达需要自然展开 | 先接住主诉，再在上下文中补齐信息 | REQ-003、REQ-016、REQ-017；对话优先路由 | `TurnInterpretation`、support/free_chat 状态、学生侧聊天截图 |
| 评估需要覆盖持续时间、情绪、功能等维度 | 建立结构化字段，但不把字段列表直接暴露给学生 | REQ-004、REQ-013、字段状态与证据 | `ConversationContext`、报告模板、结构化报告局部示意 |
| 危机信息需要优先处理，不能等普通流程结束 | 风险持续监测，危机分支中断普通对话 | REQ-005、REQ-006、REQ-007；R0/R1/R2/R3/RX | `safetyRuntime`、危机流程图、资源白名单 |
| 量表不能机械插入自然对话 | 量表按问题相关性触发，自然语言回答再映射 | REQ-008、REQ-009、REQ-010 | PHQ-9/GAD-7 设计与完整性阻断规则 |
| 报告需要可追溯，不能只有模型结论 | 保存证据、字段状态、风险依据和信息缺口，结论保持非诊断 | REQ-012、REQ-014；证据与结论分离 | 报告模板、report draft、报告示意图 |
| 后台需要自动留档，学生不应看到内部信息 | 学生侧支持性回复与后台报告分离，外发字段最小化 | REQ-014、REQ-015；四字段 payload | `report-to-feishu` 设计、审计记录、飞书截图 |

## 17. 叙事与验证语言

### 17.1 主体叙事

主体采用“最终版本应该如何工作”的完整链路来讲：学生自由表达，系统理解主诉和上下文，后台自动沉淀结构化证据，报告被创建或更新，必要信息进入外部工作流。这样 PPT 不会退化成当前开发进度汇报。

### 17.2 证据标注

每一类结果在页脚或备注中标注来源：

- `研究材料`：访谈编码、主题总结、需求提炼；
- `设计产物`：流程、规则、报告模板、数据边界；
- `本地验证`：测试、类型检查、smoke、mock 或 audit；
- `历史 synthetic 联调`：重构前 Agent 场景记录；
- `最终外部验证`：最终版本的 Agent、工作流、飞书和录屏证据。

### 17.3 必须避免的偷换

- “完成报告设计”不等于“最新版本已经被飞书真实验证”；
- “synthetic 多轮联调通过”不等于“真实学生测试通过”；
- “风险规则和资源白名单已实现”不等于“系统具备临床风险判断能力”；
- “最终版按该链路完成”不等于“可以在没有最终截图时提前宣称外部闭环已经完成”。
