## 二、对 `src/` 的详细分析

## 2.1 `src/` 当前结构

当前 `src/` 分为以下几层：

- `app/`
- `contracts/`
- `domain/`
- `services/`
- `styles/`
- `utils/`

整体上，业务分层已经是清楚的，问题主要不在层次错误，而在于以下几点：

### 1. `src/app/` 文件较多且平铺

`src/app/` 当前包含多个 runtime 文件，例如：
- `pageRuntime.js`
- `sessionRuntime.js`
- `chatRuntime.js`
- `uploadRuntime.js`
- `statusNoticeRuntime.js`
- `reportDraftRuntime.js`
- `navigationRuntime.js`
- `modelRuntime.js`

这部分的问题不是“文件太多”，而是：
- 入口层文件全部平铺在一个目录里
- 新读代码的人不容易快速分辨哪些是页面入口、哪些是会话总线、哪些是辅助 runtime

不过从职责上看，这些文件当前仍然是有边界的，不属于简单重复文件，因此本轮没有直接合并它们。

### 2. `pageRuntime.js` 与 `sessionRuntime.js` 体量偏大

当前 `src/app/` 下最重的两个文件是：
- `pageRuntime.js`
- `sessionRuntime.js`

其中：
- `pageRuntime.js` 负责页面级初始化和 legacy 全局函数兼容
- `sessionRuntime.js` 负责会话总线、阶段推进、assessment、safety、upload 状态桥接

它们确实是后续可继续拆分的重点，但这类拆分会直接影响页面初始化和会话通路，因此风险较高，不适合作为本轮“文件整理”动作直接处理。

### 3. `src/components/` 当前没有真实内容

该目录此前只有一个占位 `README.md`，没有实际组件实现。  
这意味着它目前不是一个有效工作目录，而是未来预留结构。

### 4. 多个子目录存在占位 README

以下目录此前都存在单独的 README：
- `src/components/`
- `src/domain/`
- `src/services/`
- `src/utils/`
- `src/styles/`

这些 README 单独存在时，会增加目录噪音。  
它们的内容总体上是有价值的，但更适合被整合到一个统一的 `src/README.md` 中。

### 5. `bootstrap.ts` 是空占位入口

`src/app/bootstrap.ts` 当前只是一个历史占位文件，没有参与实际运行链路，也没有被入口引用。  
因此它属于典型的“可以直接清理”的无效源文件。

## 三、对 `src/` 的整理判断

根据上面的分析，本轮对 `src/` 的判断是：

### 适合本轮直接整理的内容

- 占位 README
- 空占位入口 `bootstrap.ts`
- 空目录说明降噪
- 为 `src/` 增加一个统一结构入口说明

### 不适合本轮直接重构的内容

- `pageRuntime.js` 继续拆分
- `sessionRuntime.js` 继续拆分
- `app/` 下 runtime 子目录重命名
- `services/` 和 `domain/` 深层重组

原因是：
- 当前这些文件已经在运行链路中稳定工作
- 本轮任务的重点是“整理冗杂”，不是“重写主通路”
- 深层重构会显著提高回归风险

因此，本轮对 `src/` 采取的是：

> 清理无效项，保留有效分层，不对主运行时通路做激进重构。
